## p51

**The claim.** A stage that died into the dead-letter queue is still called
`Running` by the run trace, with an elapsed clock that counts forever. Filed
under P4.5 against post `2ed65d71-e3b0-497c-bf13-303f87ad30dd`.

### The cause is one line upstream of the symptom

`markStageRunning()` (`src/mastra/post-state.ts`) writes
`stage_status[stage] = "running"` on the way into a step, and `saveStageOutput()`
is the only thing that moves it, on the way out. A step that throws its last
attempt never reaches the second write, and `markPipelineFailed()`, the whole of
the port's dead-letter write, set `current_stage` and `stage_logs._error` and
nothing else:

```
      currentStage: CURRENT_STAGE_FAILED,
      stageLogs: sql`coalesce(...) || ...`,
      updatedAt: now,
```

So the row itself said two things: the run is dead, and the stage it died in is
executing. The trace was not the defect, it was the third reader repeating the
row faithfully. `grep -rn "STATUS_FAILED" src/mastra` finds exactly one writer
before this change, `images-assemble.ts`, for a fan-out where every image
failed: nothing in the port ever wrote `stage_status[stage] = "failed"` for a
stage that threw, which is also why the header badge read a bare `Failed`
instead of `Failed at Write` and why the post page offered no `Re-run` for it.

### The fix, in two halves

1. **The writer.** `markPipelineFailed()` takes the stage the failure named and
   merges `stage_status[stage] = "failed"` into the same statement.
   `recordRunFailure()` now reads `failedStageOf()` before the write instead of
   after it, so the stage on the announcement and the stage on the row are one
   derivation. When the engine's terminal event names no step, nothing is
   stamped: inventing one would be worse than the stale value.
2. **The reader.** `resolveStageStatus()` in `src/lib/run-state.ts` reads a
   stage the map still calls `running` under `current_stage = "failed"` as
   `failed`. It is needed for two cases the writer cannot reach: every row
   written before this change, and the unnamed-step failure above. It returns
   the same object when nothing changes. `deriveRunState()` reads through it,
   `PipelineProgress` reads through it (it already held `currentStage`, so no
   caller can forget), and `/posts/[id]` reads it once and passes it to the
   badge, the dots, the trace, the tabs and its own `isRunning`.

**The claim.** `GET /api/analytics/dashboard` counts a post whose publish died
as complete, so the completion rate and the Posts by Stage chart contradict the
stalled-publish card P4.9b put directly above them.

### At HEAD, one screen said both things about the same row

Four complete runs and two failed ones on the e2e account, one of the four
carrying a WordPress publish a worker picked up 95 minutes ago and one carrying

```
$ curl -s localhost:3000/api/analytics/dashboard -b jar

```

`ui/p52-before-rate-contradicts-card.png` is that pair rendered: the card reads
`Publishing stopped responding on 1 post`, and 40 pixels under it the stat card
reads `66.7%` over `4 of 6 runs finished cleanly`. One of those four is the post
named in the card.

### The cause

`deriveRunState()` answers about the run, and the run did finish: the six stages
are green and `markPipelineComplete()` stamped `current_stage`. Nothing was
wrong with that derivation. What was wrong is that `complete` and
`completion_rate` were presented as the answer to "did this post make it", which
is a question the publish after the run also gets a vote in, and the handler had
never read the publish columns at all. The card added at P4.9b is what made the
disagreement visible on one screen; the arithmetic under it predates it.

### The fix

`src/lib/publish-queries.ts` is new and holds `deadPublishes()`, one query for
the publishes that are not going to move again: the same
`publishColumnOf()`/`publishStall()` derivation `GET /api/queue` already used,
plus the rows whose status column says `failed` outright. `GET /api/queue` now
calls it and filters to the stalled ones (its card is unchanged), and the
dashboard calls it for the ids, so the two screens cannot answer differently.

A run that reached the end and whose own publish is in that set comes out of
`complete` and is counted under the new `publish_incomplete` instead, which is a
number rather than a silent subtraction: `/monitor` prints
`2 more finished but never published` under the two counts. A run already
`finished_with_errors` is in neither, because it has its own explanation and one
row under two of them is the confusion being fixed.

Clearing the gate of the stage a run is already parked at did not release the
run, so the gates card reported a setting the run could never act on while the
approval banner for that same stage was still on screen.

### The contradiction, in a real browser at HEAD

Dev server on :3000, signed in as `e2e-runner@jena.test`, one seeded post owned
by that account with `stage_status.outline = "review"` and
`stage_settings.outline = "review"`. Set Outline to "Run automatically" in the

    $ npx -y chrome-devtools-axi eval "() => { const s=document.querySelector('[data-testid=gate-summary]'); const banner=[...document.querySelectorAll('p')].find(p=>p.textContent.includes('waiting for your approval')); return JSON.stringify({summary: s?.textContent, banner: banner?.textContent}) }"

             "banner":"Outline is waiting for your approval"}

`ui/p53-before-cleared-gate-still-parked.png` is that page: the banner at the
top, the summary 900 pixels below it.

### Cause

Two different stores, and only one of them was written.

The gate that parked the run was read at the top of the step, before it
suspended: `reviewGate()` in `src/mastra/steps/stage-io.ts` runs inside
`execute` and `suspend(gate)` freezes the whole run into
`mastra_workflow_snapshot`. Nothing re-reads `stage_settings` for a run that has
already stopped, so `PATCH /api/posts/{id}` cannot reach it. The comment on
`handleGatesChange` was right about the case it described (a run still moving
picks a gate change up at its next stage, because every step calls
`loadPipelineState()` at the top of its `execute`) and silent about the case
where the run is not moving at all.

The one thing that does reach a suspended run is `POST /api/posts/{id}/approve`,
which is what the banner's own button calls.

### The fix

Two halves, because there are two ways the page was wrong.

1. `PipelineGatesCard` takes `parkedStages` and says where the run is stopped
   *now* before it says where it will stop next. `/posts/[id]` passes
   `runState.reviewStages`, the same derivation the banner and the header badge
   read, so the three cannot disagree. Parked at Outline with no gates left
   ahead it reads: `This post is waiting for you at Outline. After that it will
   run to Ready without stopping.`
2. `handleGatesChange` releases the run when the gate cleared is the one holding
   it: the stage is in `runState.reviewStages` and its new mode does not stop
   the run. The release goes through `posts.approve()`, the route the banner
   uses, after the row write has been accepted. A refused release does not read
   as a failed save, because the save did happen.

   true` swallows, so a cascade over posts with real media on disk is proven
   only by the single-post path it copies.

## P5.5

A run paused after its last stage could only be finished from `/posts/[id]`.
The other two screens that name that state had no way to act on it, and one of
them had a control that quietly did the wrong thing.

### The state

`isPausedBeforeFinish()` in `src/lib/run-state.ts` names it: `current_stage =
"paused"` with all six stages complete. `ready` is the only stage with no stage
after it to read the pause, so `pipeline-complete` reads it instead and skips
the three things it does for a full run, the `completed_at` stamp, the
auto-publish and the `pipeline_complete` frame. The finish is therefore work
that still has to happen, and the only endpoint that reaches it for such a row
is `POST /api/posts/{id}/run-all`: it releases the pause, starts the full form
with no stage selection, and every one of the six complete stages is skipped by
`shouldRunStage`, so the run costs nothing and reaches only the hook.

`/posts/[id]` has had that action since P4.4b, in the orange banner
(`handleFinishRun` -> `posts.runAll`). The posts list at `/` and `/monitor`
both got the badge right and neither carried the action.

`/monitor` was worse than missing it. Its only control for a paused run is
`Resume All`, and `POST /api/queue/resume-all` recovers each post's next stage
from `stage_status`; a post with no next stage was written to `current_stage =
"complete"` and nothing was started for it. That is the row a finished run
leaves minus everything `pipeline-complete` does. It was a faithful port of the
Python loop and it is wrong for the same reason P2.115 was wrong: a pause used
to be a label and is now a run state that something has to release properly.

### The fix

`POST /api/queue/resume-all` now starts every paused post it moves, not only
the ones with a stage left. A post with no next stage is started in the full
form (`startPipeline(id, undefined)`), which is the same start `POST /run-all`
makes for the same row: the six complete stages are skipped and only the finish
runs. The `current_stage = "complete"` write is unchanged, and so is `count`,
which is still the number of paused posts rather than the number of runs
started.

The row menu on `/` offers `Finish this run` in place of `Pause` when
`isPausedBeforeFinish()` says so, calling `posts.runAll(id)`, the same call the
banner on `/posts/[id]` makes. `Pause` is dropped for those rows because there
is nothing left to pause.

`/monitor`'s `Resume All` tooltip now says what the new branch does rather than
only what the other one does.

### Two existing tests changed, deliberately

`marks an all-complete post 'complete' and starts nothing for it` asserted the
defect. Its `expect(start.calls).toEqual([])` is removed and the title drops
the second clause; the new case above owns the start. `resumes several posts in
one call` asserted the same thing for the middle post of three, and now expects
all three ids with the middle one carrying no stage.

### What none of this proves

1. The end-to-end pass ran on a post with `output_format = "markdown"`, so
   `pipeline-complete` had no publish to start. The finish reaching a real
   WordPress or Next.js publish is not covered here.
2. `Resume All` acts on every paused post at once. A batch mixing ordinary
   pauses with paused-before-finish rows is covered only by the three-post
   route case, not by a browser pass.
3. The row menu decides from the list's own copy of `stage_status`, which is as
   fresh as the last fetch. A run finished in another tab leaves `Finish this
   run` on screen until the list refetches, and the press is then a no-op run
   against a complete post.
4. Nothing was added to `/monitor` itself: it has no post rows, so the finish
   there is reachable only through `Resume All`, which is all-or-nothing. A
   reader who wants to finish one of three paused runs from that screen still
   cannot.
5. `posts.pause()` on an already-paused post is still offered everywhere else
   the run is paused for an ordinary reason. Only the paused-before-finish rows
   lose it here.
