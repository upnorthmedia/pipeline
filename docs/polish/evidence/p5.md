# P5. Criterion 9, second pass

`docs/polish/LEDGER.md` P4 enumerated the `[confirmed]` entries `todo.md` held on
2026-08-24 and closed all of them. Closing them filed residuals, so the file has
`[confirmed]` entries again. P5 is the second enumeration, in severity order,
with the entries that do not meet criterion 9's bar named in the ledger as
`SUMMARY.md` gaps rather than given an item.

## p51

**The claim.** A stage that died into the dead-letter queue is still called
`Running` by the run trace, with an elapsed clock that counts forever. Filed
under P4.5 against post `2ed65d71-e3b0-497c-bf13-303f87ad30dd`.

### The cause is one line upstream of the symptom

`markStageRunning()` (`src/mastra/post-state.ts`) writes
`stage_status[stage] = "running"` on the way into a step, and `saveStageOutput()`
is the only thing that moves it, on the way out. A step that throws its last
attempt never reaches the second write, and `markPipelineFailed()`, the whole of
the port's dead-letter write, set `current_stage` and `stage_logs._error` and
nothing else:

```
      currentStage: CURRENT_STAGE_FAILED,
      stageLogs: sql`coalesce(...) || ...`,
      updatedAt: now,
```

So the row itself said two things: the run is dead, and the stage it died in is
executing. The trace was not the defect, it was the third reader repeating the
row faithfully. `grep -rn "STATUS_FAILED" src/mastra` finds exactly one writer
before this change, `images-assemble.ts`, for a fan-out where every image
failed: nothing in the port ever wrote `stage_status[stage] = "failed"` for a
stage that threw, which is also why the header badge read a bare `Failed`
instead of `Failed at Write` and why the post page offered no `Re-run` for it.

### Failing first

The strongest of the three is in the real-run suite, which runs the real
workflow on a real evented engine with `write` throwing:

```
FAIL  src/mastra/failure-recorder.test.ts > a pipeline run that fails
      > stamps the stage that threw as failed, so nothing is left calling it running
AssertionError: expected "running" to be "failed"
```

Two hand-built cases against the real database, one for the stamp and one for
the branch that cannot have it:

```
FAIL  recordRunFailure > stamps the named stage failed on the row, without disturbing the others
  {
-   "edit": "failed",
+   "edit": "running",
    "research": "complete",
  }
```

Reader side, four in `src/lib/run-state.test.ts`
(`resolveStageStatus is not a function`, plus the updated `deriveRunState` case),
one in `src/components/pipeline-progress.test.tsx`
(`expected document not to contain element, found <span class="... ring-amber-500/30 ...">`),
and two page-level cases in `src/app/posts/PostDetail.test.tsx`. The two page
cases were re-run against `git show HEAD:` copies of `page.tsx` and
`pipeline-progress.tsx` after the fix was written, to prove they fail on the
code they were written against:

```
✓ names the stage the run died in on the badge, and offers its re-run
FAIL does not leave the run trace calling the stage it died in running
FAIL stops the progress dot spinning on the stage the run died in
Tests  2 failed | 1 passed | 73 skipped (76)
```

The one that passed at HEAD passed because `deriveRunState()` was already
fixed by that point; it is the badge case and it is listed here as such.

### The fix, in two halves

1. **The writer.** `markPipelineFailed()` takes the stage the failure named and
   merges `stage_status[stage] = "failed"` into the same statement.
   `recordRunFailure()` now reads `failedStageOf()` before the write instead of
   after it, so the stage on the announcement and the stage on the row are one
   derivation. When the engine's terminal event names no step, nothing is
   stamped: inventing one would be worse than the stale value.
2. **The reader.** `resolveStageStatus()` in `src/lib/run-state.ts` reads a
   stage the map still calls `running` under `current_stage = "failed"` as
   `failed`. It is needed for two cases the writer cannot reach: every row
   written before this change, and the unnamed-step failure above. It returns
   the same object when nothing changes. `deriveRunState()` reads through it,
   `PipelineProgress` reads through it (it already held `currentStage`, so no
   caller can forget), and `/posts/[id]` reads it once and passes it to the
   badge, the dots, the trace, the tabs and its own `isRunning`.

### Gates

`pnpm exec tsc --noEmit`, `pnpm lint` and `pnpm build` exit 0.
`pnpm test`: 190 files, 5534 passed, 9 skipped, 0 failed, no worker running.
`git status --porcelain` after the suite lists only the nine changed files.

### What none of this proves

1. No row in any database was rewritten. Rows already carrying a stale
   `running` under a terminal failure still carry it; every reader in this app
   reconciles them, and nothing else reads the column.
2. `GET /api/analytics/dashboard` and `GET /api/queue` read `stage_status`
   server side and do not call `resolveStageStatus()`. Neither is wrong today
   (the dashboard already counts a `failed` + `running` row as incomplete, and
   the queue counts by run state), but they are two more readers of the raw
   column.
3. The failing run in the browser pass was seeded with SQL. The real-run
   assertion in `failure-recorder.test.ts` is what proves a worker writes the
   stamp.
4. `resolveStageStatus()` treats every `running` stage on a failed run as
   failed. A row with two of them would report both, which no run can produce
   today (the pipeline is sequential) but nothing enforces.
5. The `Running <Stage>...` empty-state copy and the read-only editor on the
   stage tabs are unreachable, so the change to them is untested: the tab
   trigger is `disabled` for a stage with no content, and a stage that threw
   has none. Filed in `todo.md`.

## p52

**The claim.** `GET /api/analytics/dashboard` counts a post whose publish died
as complete, so the completion rate and the Posts by Stage chart contradict the
stalled-publish card P4.9b put directly above them.

### At HEAD, one screen said both things about the same row

Four complete runs and two failed ones on the e2e account, one of the four
carrying a WordPress publish a worker picked up 95 minutes ago and one carrying
a Next.js publish the step recorded as `failed`:

```
$ curl -s localhost:3000/api/queue -b jar | jq '.publish_stalled[0].topic'
"Nine ways to speed up a slow WordPress site"

$ curl -s localhost:3000/api/analytics/dashboard -b jar
{"by_status":{"failed":2,"complete":4},"total":6,"complete":4,
 "completion_rate":66.7, ...}
```

`ui/p52-before-rate-contradicts-card.png` is that pair rendered: the card reads
`Publishing stopped responding on 1 post`, and 40 pixels under it the stat card
reads `66.7%` over `4 of 6 runs finished cleanly`. One of those four is the post
named in the card.

### The cause

`deriveRunState()` answers about the run, and the run did finish: the six stages
are green and `markPipelineComplete()` stamped `current_stage`. Nothing was
wrong with that derivation. What was wrong is that `complete` and
`completion_rate` were presented as the answer to "did this post make it", which
is a question the publish after the run also gets a vote in, and the handler had
never read the publish columns at all. The card added at P4.9b is what made the
disagreement visible on one screen; the arithmetic under it predates it.

### The fix

`src/lib/publish-queries.ts` is new and holds `deadPublishes()`, one query for
the publishes that are not going to move again: the same
`publishColumnOf()`/`publishStall()` derivation `GET /api/queue` already used,
plus the rows whose status column says `failed` outright. `GET /api/queue` now
calls it and filters to the stalled ones (its card is unchanged), and the
dashboard calls it for the ids, so the two screens cannot answer differently.

A run that reached the end and whose own publish is in that set comes out of
`complete` and is counted under the new `publish_incomplete` instead, which is a
number rather than a silent subtraction: `/monitor` prints
`2 more finished but never published` under the two counts. A run already
`finished_with_errors` is in neither, because it has its own explanation and one
row under two of them is the confusion being fixed.

### Failing first

Seven route cases against the real database, before the route changed. The two
that fail on the count itself rather than on the missing key are the item:

```
FAIL src/app/api/analytics/dashboard.test.ts > complete and a publish that did
     not land > leaves a complete run whose publish stopped moving out of complete
AssertionError: expected 2 to be 1

FAIL ... > leaves a complete run whose publish failed out of complete
AssertionError: expected 1 to be +0
```

The other five (`expected undefined to be +0`) are the new key not existing yet:
inside the window, never attempted, a status column the row's format does not
name, a run already finished with errors, and another user's row.

And the screen, in `QueueMonitor.test.tsx`:

```
FAIL src/app/monitor/QueueMonitor.test.tsx > MonitorPage > names the finished
     runs a dead publish keeps out of the rate
TestingLibraryElementError: Unable to find an element with the text:
1 more finished but never published
```


`ui/p52-after-rate-names-the-gap.png`: the card is unchanged, and under it

### Gates

`pnpm exec tsc --noEmit`, `pnpm lint`, `pnpm test` (190 files, 5543 passed, 9
skipped, no worker running) and `pnpm build` all exit 0, and `git status` after
the suite shows only this change's files.

### What none of this proves

1. The `failed` half of `deadPublishes()` has no surface of its own on
   `/monitor`. A user sees the count go down and the amber line say why, but the
   posts behind it are only findable from the posts list.
2. `publish_incomplete` is uncapped in the same way the P4.9b card is: it is a
   number rather than a list, so the cost is a count, but it says nothing about
   which posts.
3. The browser pass seeded its four rows with SQL. No real publish was run, so
   what is proven end to end is the derivation and the render, not that a real
   WordPress failure lands in the column this reads.
4. A publish still inside the 15 minute window keeps its row in `complete`, so
   the number moves on its own when the window closes with nothing else having
   happened. The 10s refetch on the tab is what makes that visible.
5. `avg_duration_s` still averages `completed_at - created_at` over every row
   with a `completed_at`, including the ones now counted under
   `publish_incomplete`. That average is about the run, which is defensible, but
   it is a third rule on this screen and nothing says so on it.
