### Root cause

The component did not drop the testid. `ImagePreview` guards on
`!manifest.images || manifest.images.length === 0` (`web/src/components/image-preview.tsx:56`)
and returns the empty state before it ever reaches the `data-testid`. Each of the six fixtures
passed a flat map keyed by image id:

```ts
const manifest = { featured: { prompt: "...", alt_text: "...", placement: "Featured image" } };
```

That shape has never been produced by anything in this repo:

* `rules/blog-images.md:127-172`, a fixed contract, asks the model for
  `{ model, style_brief, images: [ { id, type, filename, prompt, alt_text, placement: { location, after_section }, ... } ] }`.
* `parseManifest` (`web/src/mastra/images/manifest.ts`) passes that document through
  unchanged, and its parse-failure fallback is `{ images: [], style_brief: {}, error }`.
* `foldManifest` (`web/src/mastra/steps/images-assemble.ts:78`) writes
  `{ ...manifest, images, total_generated, total_failed }` into the `image_manifest` column,
  and that is the stage's only write.
* `generateOneImage` (`web/src/mastra/images/generate-one.ts:213`) returns each entry as
  `{ ...spec, generated: true, size_bytes, url: "/media/<postId>/<filename>", index }` on
  success and `{ ...spec, generated: false, error, index }` on failure.

`git log --follow web/src/components/image-preview.tsx` reaches the repo's first commit
(`0018f3c`) with the `images?: ImageEntry[]` interface already in place, so there is no
version of this component the flat fixtures ever matched. The fixtures are the broken side.

Two of the six also asserted behaviour that would be a defect if the component had it:

* `placement` was a bare string. The contract makes it an object, and the stage's own comments
  record that real manifests always write it as one.
* `filename` was expected to be rendered as an `<img src>`. `filename` is the name the *model*
  asked for, and for a featured image the stage rewrites it to
  `featured-MMDDYY-XX.<ext>` before writing the file, so rendering it as a src produces a
  broken image. Only `url`, set after the write, is a path this app serves.

### The fix

Six fixtures rewritten onto the stored shape, with the assertions' intent kept:

| test | before | after |
| --- | --- | --- |
| renders image cards from manifest | flat map | `images: [{id: "featured"}, {id: "content-1"}]`, same three assertions |
| displays alt text | flat map | one `images` entry, same assertion |
| displays placement info | `placement: "Featured image"` | `placement: { location: "after_heading", after_section: "Choosing A Router" }` |
| displays prompt text | flat map | one `images` entry, same assertion |
| displays style metadata | per-entry `style` | `style_brief.overall_style`, which is where the contract puts it |
| displays image with filename | expected `filename` as `src` | renamed to "does not render the model's declared filename as an image src", asserts no `<img>` |

`makeCompletedPost()` in `web/src/test/fixtures.ts` carried the same flat map
(`image_manifest: { featured: { prompt: "A test image" } }`) and was rewritten onto the stored
shape as well. No `PostDetail.test.tsx` assertion reads the manifest, and all 18 of its tests
still pass.

No production file was changed. `git diff --stat` covers only the two test files.

## P0.2

`src/mastra/workflows/scaffold-check.test.ts` ran on the app's own Mastra instance,
transport and default Redis key prefix. Mastra's orchestration topic is a Redis Streams
consumer group, so each event on it is delivered to exactly one consumer. Any other consumer
on `mastra:topic:workflows` (a real worker, a stray `mastra dev`, or another test file that
calls `startWorkers()` on the app instance) claims this run's `workflow.step.*` events, and
the drained `fullStream` comes up short.

### Fix

The suite now builds its own instance on a prefixed transport, which is the pattern the
other fourteen workflow suites already use (`mastra:test:pipeline`,
`mastra:test:review-gates`, `mastra:test:images`, and so on). The three process-level
suites that cannot use `keyPrefix`, because they boot the production bundle with the
production pubsub config, take whole Redis databases instead: `worker-process` (9),
`web-restart` (10), `crash-probe` (11).

```ts
const pubsub = new RedisStreamsPubSub({
  url: process.env.REDIS_URL!,
  keyPrefix: "mastra:test:scaffold-check",
})
const storage = new PostgresStore({ id: "scaffold-check-test", pool: getPool() })
const testMastra = new Mastra({ storage, pubsub, workflows: { scaffoldCheck: scaffoldCheckWorkflow } })
```

Three details worth recording:

- `testMastra` is constructed after the `../index` import has evaluated, so it is the last
  instance to register `scaffoldCheckWorkflow` and therefore the one the run is published
  through. The app instance is still imported, because the first assertion is specifically
  about the app instance's registry and must keep reading it.
- `beforeAll` clears the two prefixed topics before starting workers, so a previous run of
  this suite that died mid-stream cannot leave events for the next one. `reclaim-duplication`
  does the same.
- `afterAll` closes the app transport as well as the test one, matching `index.test.ts`,
  because importing `../index` constructs it either way.

### The upstream cause, and what this does not prove

`todo.md` carries six more entries (P2.20, P2.29, P2.36, P2.60, P2.73, P2.78) describing the
same test failing intermittently under a *full* suite run with no external worker, and
several of them guess at load or scheduling. The actual mechanism is the same one:
`src/mastra/crossprocess-events.test.ts:109` also calls `mastra.startWorkers()` on the
production instance and the default topic, and vitest runs files in parallel forks. Two
consumers in the same group, whichever way they happen to interleave. That also explains the
otherwise strange observation in P2.60 that adding *any* test file flips the result: it
changes how the fast node-environment files pack against the slow real-transport ones, and so
whether those two overlap.

whole-suite timing pressure to line up. So P2.20, P2.29, P2.36, P2.60, P2.73 and P2.78 are
left open here and belong to P0.3, which runs the full suite three times and can actually
settle them.

`crossprocess-events.test.ts` is now the only in-suite file left on the default topic. It
passed 3/3 with a live worker up, so it is not a confirmed defect, but it is structurally
exposed to the same theft. Logged in `todo.md` for P0.3.

## P0.3a

The first child of P0.3: the `settings.api_keys` row nine test files borrow. The other three

### Root cause

`settings.api_keys` is one row for the whole database: nothing writes it with a `user_id`, and
Alembic 012's NULLS NOT DISTINCT constraint allows exactly one row without one, which is the
row `getApiKeys()` reads (`web/src/mastra/api-keys.ts:43-47`). Nine test files need their own
fixture in it, so each one snapshotted the row into a module-level `savedRow`, wrote a
placeholder over it, and wrote the snapshot back in `afterAll` under a Postgres advisory lock
that serialised the files against each other.

The lock makes the files not race. It does nothing about the snapshot living in the borrower's
memory. Two consequences, both recorded in `todo.md`:

1. A borrower that dies between the snapshot and the restore takes the developer's real keys
   with it. That is not hypothetical: it happened during port item 6.0 and the row was
   recovered from the Postgres WAL.
2. The next run then snapshots the *placeholder* the dead run left and writes it back as if it
   were the developer's keys, so the placeholder becomes permanent and every later run
   restores it.

### The failing test

`web/src/test/borrowed-rows.test.ts` drives the real borrow code on its own throwaway
`settings` keys and its own advisory lock, so it never touches `api_keys`. Run against the
in-memory semantics (the leftover-backup branch removed, which is exactly what the nine files
did before this change):

### The fix

The snapshot moves out of the borrower's memory and into the database.
`web/src/test/borrowed-rows.ts` writes the pre-borrow values into a backup row in `settings`
under a key no production code reads, and the return reads them back from there and drops the
backup. A borrower that dies leaves the backup behind, and the next borrower finds it, repairs
the rows from it, and keeps it as its own backup. Recovery therefore needs no live process, and
the value restored is always the last one written from outside a borrow.

`api_keys_validation` is a second global singleton read by the same settings page, so it is
borrowed alongside and a file that touches one of the two can no longer leave the other behind.
`WP_ENCRYPTION_KEY` travels with the borrow for the same reason: every one of the nine files
was hand-rolling its save and restore.

`web/src/test/api-keys-row.ts` is now that one instance, and the nine files call
`borrowApiKeysRow({ encryptionKey: TEST_KEY })` and `returnApiKeysRow()` instead of about 30
lines each of snapshot and restore.

## P0.3b

`pipeline-events.test.ts > a run that executes every stage > carries Python's log payload and
nothing else` reads the first `log` event the `outline` stage sent and about one run in four
gets a later one instead. P0.3b asks which of the two candidates reorders the events: the
Redis Streams fan-out, which would also reorder the dashboard's live feed and would matter to
the trace view, or the recording subscriber in the test.

### The answer: the subscriber, and the transport is in order

`node_modules/@mastra/redis-streams/dist/index.js` reads a stream and dispatches its entries
one at a time, in stream order:

```js
for (const stream of result) for (const entry of stream.messages) {
  if (sub.stopped) return;
  sub.lastId = entry.id;
  await this.#deliverMessage(sub, entry.id, entry.message);
}
```

but `#deliverMessage` does not await the callback:

```js
const result = sub.cb(event, ack, nack);
if (result && typeof result.catch === "function") result.catch(async () => { await nack(); });
```

So invocation order is the topic's order and completion order is not. The test's subscriber
awaited a `readPost()` before pushing the event into `received`, so what decided the order of
that array was which database query came back first.

The three `outline` log lines are published serially from one step
(`src/mastra/steps/outline.ts:56,59,67`, each `await publishStageLog(...)`), so they cannot
reach the stream out of order. Nothing in the transport or the producer could produce the
observed symptom; the recorder could and did.

The dashboard's own subscriber is already correct: `src/app/api/events/stream.ts:137` builds a
`tail` chain for exactly this reason ("Publication order, preserved across an asynchronous
`matches`"). The live SSE feed and the trace view were never affected, and this is a
test-harness defect only.

### Measured on the real transport

`src/test/in-delivery-order.test.ts` is new and separates the two candidates against a real
`RedisStreamsPubSub`. Eight events are published in order onto a private key prefix. One
subscription records each event twice, once synchronously in the turn the transport invoked it
in and once after an `await` whose latency descends with the event index; a second subscription
runs the same awaited body through the new `inDeliveryOrder` wrapper.

```
 ✓ the Redis Streams fan-out > invokes a subscriber in publication order
 ✓ a subscriber that awaits before it records > records out of publication order, ...
 ✓ a subscriber that awaits before it records > still receives every event, ...
 ✓ the same subscriber wrapped in inDeliveryOrder > records in publication order
 ✓ inDeliveryOrder itself > runs handlers one at a time, so no two overlap
 ✓ inDeliveryOrder itself > does not let a handler that throws stall the ones behind it
 Test Files  1 passed (1)
      Tests  6 passed (6)
```

The transport delivers in order, the awaited recorder does not, and the wrapper restores it.
The "still receives every event" test pins that the gap is order and not loss, so no future
reading of this can blame a dropped event.

### The fix

`web/src/test/in-delivery-order.ts` wraps a subscriber so its body runs in delivery order:

```ts
export function inDeliveryOrder<A extends unknown[]>(
  handler: (...args: A) => void | Promise<void>,
): (...args: A) => Promise<void> {
  let tail: Promise<void> = Promise.resolve()
  return (...args: A) => {
    const delivery = tail.then(() => handler(...args))
    tail = delivery.catch(() => {})
    return delivery
  }
}
```

The chain is extended synchronously, inside the turn the transport called the listener in,
which is what makes the order the topic's rather than the event loop's. It is the same
discipline `stream.ts` already uses in production, factored so a test can share it.

Applied to the two suites that record an event after an awaited row read:
`src/mastra/pipeline-events.test.ts:258` and `src/mastra/failure-recorder.test.ts:290`.

## P0.3c

`todo.md`'s P2.8 entry blamed the intermittent agent-suite failures on two shared things:
the global `settings.api_keys` row, which P0.3a moved into the database, and the suites that
swap `globalThis.fetch`. This item is the second half. It asks whether a swap can outlive the
test that installed it, and makes the answer structural rather than a matter of every author
remembering an `afterEach`.

### Measurement, before any fix

Eleven files replace the global transport. A leak is silent by construction: the swap answers
whatever the next test asks for, so the next test still passes, just against the wrong
transport. To make it visible, a temporary guard went into `src/test/setup.ts`:

```ts
const __pristineFetch = globalThis.fetch
beforeEach(() => {
  if (globalThis.fetch !== __pristineFetch) { /* repair and throw */ }
})
```

`beforeEach` is the one point with no ordering ambiguity: it runs after the previous test's
`afterEach` hooks and after the enclosing suites' `beforeAll` hooks, so a swap still standing
there has outlived its scope. A full `pnpm test` with that guard in place:

```
Test Files  3 failed | 140 passed (143)
      Tests  26 failed | 4597 passed | 7 skipped (4630)
```

Three files, and they are not the ones P2.8 named:

| File | What it does | Verdict |
| --- | --- | --- |
| `src/lib/api.test.ts` | `vi.stubGlobal("fetch", ...)` in `beforeEach`, `vi.restoreAllMocks()` in `afterEach` | leaks: `restoreAllMocks` puts spies back and leaves stubbed globals alone. Only `vi.unstubAllGlobals()` undoes a `stubGlobal`. |
| `src/mastra/steps/images-generate.test.ts` | `vi.spyOn(globalThis, "fetch")` in three separate `beforeAll` hooks, restored once in the file's `afterAll` | leaks between suites, and the file said so: a comment on the third suite explained that it installs its own transport because "earlier suites ... leave them installed". |
| `src/app/settings/stage-models-to-provider.test.tsx` | one router installed in the file's `beforeAll`, restored in the file's `afterAll` | correctly scoped to the file, but installed by hand, so the guard could not tell it apart from a leak. |

The eight files P2.8 pointed at (`agents/{images,ready,edit,write,outline}.test.ts`,
`api-key-validator.test.ts`, `api/settings/api-keys/route.test.ts`, and `images/gemini.test.ts`
with its `vi.unstubAllGlobals()`) did **not** leak. Their hand-rolled `afterEach` restores
correctly on every path the suite exercises. So the `globalThis.fetch` half of P2.8 does not
reproduce for the suites it accused, and the leaks it missed are in three other files.

### The fix

`web/src/test/swapped-fetch.ts` is now the only way this repo swaps the global transport:

* `swapFetch(handler)` restores through `onTestFinished`, which vitest runs on every path a
  test can end on, including a failed assertion and a timeout. There is no `afterEach` to
  forget. It returns `{ realFetch, restore }`: `realFetch` for handlers that answer some hosts
  and let the rest through, `restore` for the one test that wants the transport back
  mid-test.
* `swapFetchForSuite(handler)` is for a genuinely suite-wide transport. Called in the suite
  body, it registers its own `beforeAll`/`afterAll` pair, so the swap covers exactly the suite.
* Both refuse to install over a swap they did not make. That is the mistake that turns a
  restore into a permanent replacement: capture an existing fake as "the real fetch", restore
  *that* later, and the fake is now the transport for good.
* `assertFetchNotLeaked()` is the temporary guard made permanent, and now compares against the
  stack of live swaps rather than against the pristine value, so a suite-scoped swap is
  sanctioned while it is live and a leak is not. It repairs the transport before throwing, so
  the rest of the file still runs against something sound.

Migrations: the three leaking files onto the two helpers (`api.test.ts` keeps `vi.stubGlobal`
and gains the missing `vi.unstubAllGlobals()`), and the seven hand-rolled per-test swappers
onto `swapFetch`, which deletes the `let restoreFetch` / `afterEach` / `restore` boilerplate
each had copied. `images/gemini.test.ts` already restores through `vi.unstubAllGlobals()` and
is left as it is.

One behavioural note on `images-generate.test.ts`: the third suite's comment claimed it needed
its own transport because earlier suites left failing ones installed. That is no longer true,
so the comment now says the real reason, which is that it reads the URL of a call it makes
itself.

## P0.3d

Post ids colliding across files, which vitest runs in parallel against one database.

### The defect class, and why nothing caught it

`todo.md` records it happening twice, both times expensively:

* `pipeline-completion.test.ts` reused `review-gates.test.ts`'s `...04c1/04c2/04c3`. Both files
  went intermittently red with symptoms that pointed nowhere near the cause: runs reported
  `suspended` on gates they never configured, and a `duplicate key ... posts_pkey` appeared two
  lines after the matching delete.
* `stage-log.test.ts` and `pipeline-start.test.ts` shared `...55d1`, seen as 6 failures in one
  full-suite run and 0 in the one before it.

Each file's `beforeEach` deletes its rows and re-inserts them. Run two such files in parallel
against one Postgres and the delete of one lands between the delete and the insert of the
other, so the loser fails on the primary key or, worse, reads a row the other file wrote. The
failure always surfaces in the file that lost the race rather than the one that caused it,
which is what made both sightings cost a debugging session.

Nothing in the suite made a collision visible. 56 files call `db.insert(posts)` directly, there
is no shared seeding helper, and the convention of deriving ids from the ledger item number
makes a repeat likely rather than unlucky.

### The registry

`src/test/unique-test-ids.test.ts` is the registry, and the filesystem is its storage: **a UUID
literal belongs to exactly one test file.** It scans every `src/**/*.test.{ts,tsx}`, collects
UUID literals, and fails listing every id that more than one file spells out.

The rule is deliberately stricter than the defect requires. Two files may share a literal
harmlessly when neither inserts it, or when they insert into different tables. Checking *that*
needs to know what every literal is for; checking uniqueness does not, and the escape hatch
costs one import: an id that is genuinely shared moves into a module under `src/test/`, which
is also the only way to say out loud that it is shared. `src/test/absent-ids.ts` is that
module, and it holds the three ids that nothing ever inserts.

### The blocker: P2.90, and why it only fired under load

`images-manifest.test.ts` froze `Date` for every test so the row and log stamps it asserts on
could be compared exactly against the fixture's `captured_at`:

```ts
vi.useFakeTimers({ toFake: ["Date"], shouldAdvanceTime: true })
```

`shouldAdvanceTime` is not about whether timers fire. With `toFake: ["Date"]` the timers are
real either way; what the flag does is install a real interval that pushes the *fake* clock
forward as real time passes. `@sinonjs/fake-timers`, which vitest bundles rather than
installs as a separate package, does that with a real interval whose period is
`advanceTimeDelta`:

```

                null,
                clock,
                config.advanceTimeDelta,

            const intervalId = _global.setInterval(
                intervalTick,
                config.advanceTimeDelta,

3076:        config.advanceTimeDelta = config.advanceTimeDelta || 20;
```

so the clock the test froze moves in 20ms jumps for as long as the test runs. That is the
exact shape of what was recorded: an assertion on a stamp written mid-step is correct while
the step finishes inside one tick and 20ms late when a tick lands inside it. Under a lightly
loaded machine the step takes a few milliseconds and wins; under whole-suite contention it
does not.

`images-assemble.test.ts:260` already ran with `shouldAdvanceTime: false` for the neighbouring
reason (it computes a stage duration from the clock), so the correct value for this file was
already sitting one directory over.

## P0.6b-i

`.github/workflows/ci.yml` itself, plus everything about it that can be
established without GitHub. P0.6a proved the *sequence* is sound on a fresh
macOS clone; this item writes the workflow that runs it, and then runs that same
sequence on Linux, which is the platform the workflow actually targets. Pushing
the branch and pasting a green run URL is P0.6b-ii, and it needs this commit to
exist first.

### The workflow

One job, `gates`, on `ubuntu-latest`, with `postgres:17-alpine` and
`redis:7-alpine` service containers health-gated the way `docker-compose.yml`
provisions them. It mirrors `web/README.md`'s documented setup rather than
inventing a CI-only path: write the one repo-root `.env`, `pnpm install
--frozen-lockfile`, `pnpm db:migrate`, `pnpm auth:migrate --apply`, then tsc,
lint, test, the clean-tree check, build, `playwright install chromium` and e2e.

Four decisions worth stating:

* **`pnpm/action-setup` needs `package_json_file: web/package.json`.** There is
  no `package.json` at the repository root, so the default lookup finds nothing
  and the `packageManager` field (`pnpm@10.26.2`) never gets read.
* **Both keys are generated per run** with the same
  `randomBytes(32).toString('base64url')` incantation `.env.example` documents,
  rather than committed. The database is thrown away with the runner and every
  suite that needs a Fernet key sets its own, so nothing has to survive the job.
  This also keeps a secret-shaped string out of the repository.
* **The clean-tree check is a step, not a promise.** `git status --porcelain`
  runs immediately after `pnpm test`, which is Done condition 4 asserted on
  every push instead of once by hand at P0.4.
* **Nothing creates the `mastra_*` tables in the workflow.**
  `src/test/global-setup.ts` does it once for the suite (P0.6a). A CI step doing
  it too would hide a regression in that hook.

Action versions were read from the GitHub API rather than remembered, and all
four major tags resolve: `actions/checkout@v7`, `actions/setup-node@v7`,
`pnpm/action-setup@v6`, `actions/upload-artifact@v7`.

`actionlint 1.7.12` on the file: exit 0, no output. (Its shellcheck pass is a
no-op here: shellcheck is not installed on this machine, so the `run:` block
bodies were not statically checked.)

### What the Linux dry run found: the harness is less patient than its tests

The rig is P0.6a's, on a Docker network instead of published ports: a throwaway
`postgres:17-alpine`, a throwaway `redis:7-alpine`, the working tree copied
without `node_modules`, `.next`, `.mastra` or `.env`, and a `node:22-bookworm`

### The failing test, written first

`src/test/wait-budgets.test.ts` asserts the invariant rather than the symptom:
it scans every test file for declared budgets and compares the largest against
`task.timeout`, which is the effective per-test timeout Vitest hands the test
context (`@vitest/runner` `Test.timeout`).

```
$ pnpm exec vitest run src/test/wait-budgets.test.ts --testTimeout=5000

AssertionError: the slowest declared wait is 30000ms at
src/app/api/queue/dead-letter-clear.test.ts:202
(async function waitForError(postId: string, timeoutMs = 30_000): Promise<void> {),
but vitest cuts a test off at 5000ms, so that wait can never report what it was
waiting for: expected 5000 to be greater than 30000
```

Kill checks, one mutation per pass:

| Mutation | Result |
| --- | --- |
| `--testTimeout=5000` (the pre-fix default) | 1 failed, message above |
| Delete `testTimeout: 45_000` from `vitest.config.ts` | 2 failed: the runtime one, and `vitest.config.ts declares no testTimeout` |

The third test in the file is the anti-vacuity guard: a regex that stopped
matching the codebase would make the first assertion pass over an empty list, so
it pins that at least ten budgets across at least five files are found, one of
them `events.test.ts`.

### The fix

`vitest.config.ts` sets `testTimeout: 45_000`, above the largest budget any test
declares (30_000), so a wait can always reach its own deadline and say what
never arrived. Nothing gets slower: the number only bounds a failure.

`playwright.config.ts`'s `webServer` block is hardened for CI in the same pass,
because it is the one part of the sequence P0.6a explicitly could not check:

* `reuseExistingServer: !process.env.CI`. Silently adopting a stale server is a
  way to test the wrong build, and on a runner there is never one to adopt.
* `timeout: process.env.CI ? 120_000 : 30_000`. Measured here with `.next`
  deleted: `next dev` reports `Ready in 386ms` and the first request answers
  307 about a second later, because `src/middleware.ts` redirects before the
  page compiles. A two-core runner is not this machine, and a `webServer`
  timeout is fatal rather than retried.
