## P3.1a

**The item.** P3.1 asks where each concern lives when settings, profiles and per-post
configuration overlap, with the reasoning written down. It is split three ways, and this is
the first child: the decision record, plus the surface the decision settles first,
`/posts/new`. It closes **P2.111** (`/posts/new` has no per-post pipeline configuration, so a
post created there silently takes the profile's gates with no indication that it did).

### The decision

Three owners, and each concern belongs to exactly one of them.

| Owner | Surface | What it owns | Why |
| --- | --- | --- | --- |
| Account | `/settings` | Provider API keys, per-stage model choice, `rules/*.md` | One set of credentials and one set of prompts for every site the account runs. Nothing here varies per site, so putting a copy on a profile would mean N places to rotate a key. |
| Site | `/profiles/[id]` | Identity (name, URL, niche, audience), voice (tone, word count, brand voice, avoid, required mentions), image style, publishing connections (WordPress, Next.js), sitemap and internal links, and the defaults new posts start from including `default_stage_settings` | Everything a destination needs to be written for and published to. Publishing is the case that forces this: both publish steps read their credentials off the linked profile, so the connection has to live where the link points. |
| Post | `/posts/new`, `/posts/[id]` | Topic, slug, intent, article type, keywords, competitor URLs, and per-run overrides of the site's writing values plus the WordPress category and author | The one article. Every value here starts as the site's and is then editable for this run only. |

Two rules fall out of that table, and `/posts/new` broke both.

1. **A value copied from another owner says where it came from.** Eight fields on the form
   (`niche`, `target_audience`, `tone`, `word_count`, `output_format`, `website_url`,
   `brand_voice`, `avoid`, `related_keywords`) are filled from the profile the moment one is
   picked, and are then plain editable inputs. Nothing said they were copies, and nothing said
   an edit was for this post rather than for the profile.
2. **A setting the post cannot own is shown, not hidden.** `stage_settings` decides which of
   the six stages parks the run in front of a reviewer. The post row carries it, but the value
   is the profile's: `applyProfilePrefill` in `src/app/api/posts/prefill.ts` copies
   `default_stage_settings` over it. The form never mentioned it, so a run that stopped at
   Outline stopped for a reason that had never appeared on any screen the user had been on.

### Why the gate card is read-only

`applyProfilePrefill` copies `default_stage_settings` onto the post whenever the submitted
`stage_settings` equals the schema default, which is six `auto`s:

```ts
if (equalsDefault(filled.stage_settings, POST_CREATE_DEFAULTS.stage_settings)) {
  // Copied without a null guard, so a profile that has none clears the post's.
  filled.stage_settings = profile.defaultStageSettings
}
```

So a per-post editor that let a user clear every gate would send six `auto`s and have the
profile's gates written straight back over them, with a 201 and no warning. "Clear one gate,
leave another" would survive; "clear them all", the case a user reaches for most, would not.
Until that rule changes, an editor here would be an edit the server discards. The honest
surface is one that says what the run will do and points at the profile where it is decided,
which is also what the ownership table says: gates are a site concern.

That prefill asymmetry is a real trap and is filed as a new `todo.md` entry rather than fixed
here, because changing it rewrites a rule the Python parity oracle in
`src/app/api/posts/create.test.ts` asserts.

### The two fallbacks, which disagree

`effectiveStageMode()` in `src/lib/stages.ts` is a function rather than an index because the
pipeline reads a missing value two different ways:

- A post whose whole `stage_settings` column is null runs every stage unattended:
  `post.stageSettings || defaultStageSettings()` in `src/mastra/post-state.ts`.
- A column that names *some* stages parks the run at the ones it leaves out:
  `DEFAULT_GATE_MODE` in `src/mastra/steps/stage-io.ts` is `"review"`, because Python read the
  column with `.get(stage, "review")` and failed safe towards the human.

So a profile row holding `{"research": "auto"}` stops the run at the five stages it does not
name. A card that assumed `auto` for an absent key would show a run that never stops and then
stop it. `stage-modes.test.ts` cross-checks both constants against the step module.

### Two decisions worth the words

**One form, three tabs, and a save bar bound by id.** Every field on the page is React state,
not an uncontrolled input, so a tab the user has left keeps its edits: `handleSave` reads the
state, not the DOM. The three settings tabs are `TabsContent` inside one `<form
id="profile-form">`; the links tab sits outside it, because the Add Link form is a form of its
own and nesting forms is invalid. The save bar is therefore outside the form too, bound with
`<Button type="submit" form={PROFILE_FORM_ID}>`, and sticky at the bottom of the viewport. That
is what makes `Re-crawl Schedule`, a profile column that lives in the crawl card, savable from
the tab it is on. Proven in the browser rather than only in jsdom: on the Internal links tab,
`Re-crawl Schedule` switched Weekly to Monthly, `Save Profile` clicked, toast `Profile saved`,
and then

```
GET /api/profiles/554c0d27-...  ->  {'name': 'Gated Blog', 'recrawl_interval': 'monthly', ...}
```

Native `required` validation no longer fires on that button, which is the correct trade here
and not a regression: with tabs, a required field on an unmounted tab does not exist to
validate, and `handleSave`'s own check ("Name and Website URL are required") is what actually
guards the submit. That check has a test older than this change.

**`?tab=` read with the History API, not `useSearchParams`.** The tab is read once on mount
from `window.location.search` and written back with `history.replaceState`. `useSearchParams`
would be the idiomatic reader, but it puts a Suspense-boundary requirement on any client page
Next may prerender, and this page renders nothing on the server anyway; `router.replace` would
cost an RSC round trip per tab click on a page that fetches everything itself. An unknown or
missing value opens `Site` rather than an empty page. The payoff is a linkable tab, and
`pipeline-gates-card.tsx` now spends it: `Edit gates in the <name> profile` points at
`/profiles/<id>?tab=defaults`, three cards down the third tab, rather than the top of the page.

## P3.2a

The first child of P3.2, and the one that has to come first: before the pipeline's state can
be readable at a glance, the one line every surface already shows about a run has to be true.
It was not. Closes `todo.md` finding P2.106.

### The defect

`markPipelineComplete()` in `web/src/mastra/post-state.ts` is unconditional, and its docblock
says why: Python's `_post_completion_hook` stamped `current_stage = "complete"` and
`completed_at` at the end of a full run without consulting `stage_status`, and the `images`
stage writes `images: failed` and *returns* rather than raising, so the chain carries on to
`ready` and ends normally. A run that produced no pictures is therefore stamped exactly like
one that produced six.

Both surfaces that summarise a run read `current_stage` alone:

- `web/src/app/page.tsx:413` and `web/src/app/posts/[id]/page.tsx:450` rendered
  `<StageBadge stage={post.current_stage} />`, and `StageBadge` printed the column's raw enum
  value uppercased in a monospace pill.

So the posts list said `COMPLETE` for a post whose own progress bar, three columns to the
right, painted a red dot, and the post page said `COMPLETE` above a run trace whose Images row
said `Failed` with the Gemini quota error underneath it. `docs/polish/ui/p32a-before-list.png`
and `p32a-before-detail.png` are that state in a real browser.

The post page also had no failure affordance at all for a stage. It has one for a failed
*publish* (`publishFailure`, added at P1.3) and one for a failed refetch, but a stage that
failed inside the run appeared only as a red dot and a red row in the trace, with no retry
next to either.

### Where the fix belongs, and where it does not

Not on the write. `markPipelineComplete()` is the run's own record of what it did and it is
accurate: the run *did* reach the end. What was wrong is that one of the two columns that
together hold the answer was being reported as the whole state. So the fix is a derivation,
`deriveRunState()` in `web/src/lib/run-state.ts`, and it is the only thing the UI asks.

**Precedence**, which is the whole content of the module and took one browser check to get
right:

| Order | Condition | Label |
| --- | --- | --- |
| 1 | `current_stage === "failed"` | `Failed` / `Failed at <Stage>` |
| 2 | `current_stage === "paused"` | `Paused` |
| 3 | a stage is `running` | `Running <Stage>` |
| 4 | a stage is `review` | `Waiting for you` |
| 5 | a stage `failed` and `current_stage === "complete"` | `Finished with errors` |
| 6 | a stage `failed` | `Failed at <Stage>` |
| 7 | `current_stage === "complete"` | `Complete` |
| 8 | no stage has moved off `pending` | `Not started` |
| 9 | anything else | the row's own stage name |

Rows 1 and 2 are above the stage map rather than below it, and that ordering is a correction
made *after* the first browser pass, not a guess. Shooting the live posts list with the map
read first showed `E2E Post Editor Topic`, a row holding `current_stage = "failed"` and
`stage_status = {"research": "running"}`, reading `Running Research`. It is not running:
`markPipelineFailed()` writes the terminal stamp without touching `stage_status`, so the
stage that threw stays `running` in the map for good. The pause endpoint has the same shape,
documented in its own route file: it "overwrites `current_stage` and nothing else", so a

## P3.2b-ii

The publish leg of the run trace. `todo.md` finding P2.108: the trace is the view built for
watching a run, and it ended at `ready`. A publish is the last thing a run does and the thing
most likely to fail on something outside this app, and the trace said nothing about it, in
either direction. Closes P2.108.

### The defect, and that it has two halves

`RunTrace` builds its table from `STAGES`, the six pipeline stages, and `buildRunTrace()`
drops every `execution_logs` entry whose `stage` is not one of them. Both publish steps write
`stage: ""`:

```
$ git show HEAD:web/src/mastra/steps/wordpress-publish.ts | grep -n 'stage: ""'
109:    stage: "",
238:        stage: "",
$ git show HEAD:web/src/mastra/steps/nextjs-publish.ts | grep -n 'stage: ""'
140:    stage: "",
```

So the reading side had no publish row at all. The writing side was thinner than the finding
says, which the grep above is the evidence for: three entries between the two steps, all of
them terminal. Neither step wrote a `publish_start` entry (both announced the start on the
bus only, and an SSE frame is gone the moment it is delivered), and `nextjs-publish.ts` wrote
nothing at all on success. A Next.js publish therefore left one durable trace of having
happened, `nextjs_published_at`, and a WordPress publish left one line with no start time in
front of it, so nothing could say how long a publish took or show one in flight.

### What changed

**The steps.** `wordpress-publish.ts` and `nextjs-publish.ts` each append a `publish_start`
entry after moving the row to `publishing` and before announcing it on the bus, which is the
row-then-trail-then-bus order both `_fail` paths already used and for the same reason: a
dashboard that refetches on the event must not read a row that has not recorded the fact yet.
`nextjs-publish.ts` gains the `publish_complete` entry it never wrote. Every publish entry now
carries `data: { target: "wordpress" | "nextjs" }`.

Both are deliberate divergences from the Python steps, on top of the failure-path divergence
the port already made for the same reason. The test that asserted `writes no execution log
entry` is replaced rather than adjusted: the behaviour it pinned is the defect.

**`data.target`, and why the message prefixes still matter.** Nothing clears the other
destination's status column, so one row can carry entries from both. Historic rows have no
`data.target`, and the only thing on them that names a destination is the message prefix the
steps already wrote (`WordPress publish failed: `, `Next.js publish failed: `,
`Published to WordPress: `). `publish-report.ts` owned two of those three as a private list;
it now owns all four as one table and exports `publishTargetOfMessage()` beside the
`publishFailureReason()` its own `lastPublishError()` was inlining. An entry that names no
destination either way is taken as the leg on screen, since it is the only account there is.

**The trace.** `buildRunTrace()` takes an optional `publish: { target, status }` and returns a
`PublishTrace | null` beside `stages`. The status comes off the row's `wp_publish_status` /
`nextjs_publish_status` column, mapped onto the stage vocabulary (`publishing` -> `running`,
`published` -> `complete`), for the same reason `stage_status` decides a stage's status: the
column is the pipeline's own record and the log is the audit trail behind it. The log supplies
what the column cannot say, which is when it started, how long it took and what went wrong.

Two rules keep it from asserting things it does not know:

- an attempt is only attributed to the destination on screen, so a post that changed format
  does not have the old destination's timing shown against the new one;
- the reason is carried only when the failure is the last publish entry on the row, because a
  retry that succeeded leaves the earlier failure's entry in place forever (the same rule
  `lastPublishError()` documents for the header banner).

Wall clock across the two entries is the duration, since no step measures a publish. It is
deliberately not added to the header's total time, tokens or cost: those are stage
measurements, a publish runs no agent, and a run total that silently included network time
would disagree with the analytics endpoints.

**The page.** `/posts/[id]` passes the column it already read for the failure banner. The
destination is `publishTargetOf(post.output_format)`, the same rule the banner uses, so a post
whose format is `both` or `markdown` shows no publish row: `both` is the column default that
no publish step handles, which is `todo.md` P2.113 and not this item.

## P3.2c

Live image events. `todo.md` finding P2.47: `NAMED_EVENTS` in `web/src/hooks/use-sse.ts`
listed eight names and neither `image_generated` nor `image_failed` was among them, so
`images` was the one stage whose progress never reached an open page. Closes P2.47.

### The defect

`EventSource` delivers a frame carrying an `event:` field only to a listener registered for
that exact name. It never reaches `onmessage`. So a name missing from `NAMED_EVENTS` is a
frame the browser receives, parses and discards.

```
$ git show HEAD:web/src/hooks/use-sse.ts | grep -c 'image_generated\|image_failed'
0
$ grep -n 'event: "image_' web/src/mastra/steps/images-generate.ts
141:        event: "image_generated",
150:    event: "image_failed",
```

Both lines are published by the fan-out, one per manifest entry, and both are stored on
`posts.execution_logs`. The stored copy is why this reads as a display gap rather than a lost
signal: the events existed, nothing on the client asked for them, and nothing on the client
read the stored ones either. `buildRunTrace()` switches on four event names and let both fall
through its `default`.

`images` is the only stage where this matters, because it is the only stage whose work is a
fan-out. The other five are one prompt and one answer, so `running` says everything there is
to say. For `images`, `running` hides how much of the work is done and `complete` hides that
some of it failed: a stage that generated no images at all still finishes and still writes
`complete` (that is P3.2a's `finished_with_errors`, from the other direction).

### What changed

**`web/src/hooks/use-sse.ts`.** The two names join `NAMED_EVENTS`, with a docblock stating
the `EventSource` rule so the next name added to the pipeline is not dropped the same way.

**`web/src/lib/run-trace.ts`.** `StageTrace` gains `images: ImageProgress | null`, counted
from the stored `image_generated` / `image_failed` entries. Four rules decide the count:

| Rule | Why |
| --- | --- |
| Keyed on `data.index`, last outcome wins | The fan-out retries a failed image, which publishes a failure and then a success for the same manifest entry. Counting entries would count that image twice. |
| An entry with no index gets a key of its own | Two failures with nothing to tell them apart are still two failures. |
| An `images` `stage_start` clears the counts | The stage regenerates every image, so the previous attempt's are not this one's. |
| A stage the row has disowned clears them | `POST /rerun` resets the stage and deletes its files while `execution_logs` keeps the finished attempt's lines. Same argument the module already applies to a disowned `stage_complete`'s tokens and cost. |

`liveImages` is the new input beside `liveStart`, for the same reason that one exists: the
frames arrive one at a time and nothing refetches the row until the stage ends. Live frames
land on top of the stored ones under the same keys, so an image in both counts once. They
replace the stored trail entirely when `liveStart` names `images` at an instant later than the
last stored `images` `stage_start`, which is the retry button: the page has seen the stage
start again and the row has not been refetched since.

**`web/src/components/run-trace.tsx`.** The `images` row gains a detail line under it:
`5 images generated`, `3 images generated, 2 failed`, or `2 images failed` when none
succeeded. Amber when anything failed, muted otherwise. Both halves are counted rather than
only the failures, because "4 of 5 generated" and "none generated" read the same when only
the failures are shown.

**`web/src/app/posts/[id]/page.tsx`.** The two names join `debugEvents`, so each per-image
line appears in the Debug Logs panel with the message and level it was published with, and
the page keeps the frames it has seen since the stage started, clearing them on an `images`
`stage_start`.

## P3.3a

The route error boundaries. Closes `todo.md`'s P2.96.

### Root cause

Three files rendered the exception's own message as the body copy:

```
src/app/error.tsx:22               {error.message || "An unexpected error occurred."}
src/app/posts/[id]/error.tsx:24    {error.message || "An unexpected error occurred."}
src/app/profiles/[id]/error.tsx:24 {error.message || "An unexpected error occurred."}
```

`grep -rn 'error\.message\|err\.message\|\.stack' src/app src/components src/hooks` outside
`src/app/api/` returns those three lines and nothing else, so the whole of P3.3's "no stack
traces in the UI" complaint is these three files.

The reason it is always the wrong thing to print is not that exception messages are ugly. It
is that **no boundary here can ever receive an error a user could act on.** Every request the
dashboard makes goes through `request()` in `src/lib/api.ts`, which throws an `ApiError`, and
every page that makes one catches it and renders the server's own complaint through
`apiErrorMessage()` (`src/app/posts/[id]/page.tsx:131` is the post page's, and its docblock
records why: a failed load used to bounce the operator to `/`). Nothing routes a fetch failure
to a boundary. What is left is a render-time exception, and V8 words those for whoever is
reading the stack.

`apiErrorMessage()` already makes exactly this call one layer down, for a response body that
is not JSON: *"Not JSON: a network failure or an HTML error page. Neither is worth showing to
a user, so the caller's own wording wins."* The boundaries were the one place that rule was
not applied.

The old heading was wrong for the same reason. "Failed to load post" describes a load, and by
the time a render-time exception reaches this boundary the load has already succeeded: the
page has the post and something downstream of it threw.

### What changed

`src/components/route-error.tsx` is the body all three boundaries render. It takes the title,
optional back-link actions and the error; it logs the error in an effect the way each file
did, so the stack still lands in devtools; and it renders:

- the title, in the user's terms, per route ("This post could not be displayed");
- one sentence of body copy that says what class of failure it is and what it did not touch
  ("This is a display failure, so nothing has been changed or lost."), then what to do;
- `Back to Posts` / `Back to Profiles` where the route has somewhere to go, then `Try again`;
- a closed `<details>` disclosure holding `technicalDetail(error)` and the digest.

`technicalDetail()` is `name: message`, falling back to the name alone when the message is
empty, which is the "no `undefined` in the UI" half of P3.3: an error thrown with no message
would otherwise render a blank line, and one read off a plain object would render the string
`undefined`.

Keeping the message rather than dropping it is deliberate. A digest alone is useless without
server log access, and the person who hits this is usually the person who has to report it.
One click is the right distance: not the headline, not gone.

### The other half of P2.96 does not reproduce

`execution_logs`, taking the whole page down instead of one panel. Measured, three ways, and

mismatch, not a server response"); the mismatch it was seen through was a stubbed payload
during the P0.5b e2e work, which no longer exists. Deleted rather than fixed: adding a
tolerant branch would be dead code with no test that can reach it. The general form of the
complaint, that one panel throwing takes the page down, is a panel-level boundary question
and belongs to P3.4 if it is worth anything, not here.

### The fix, and why it reaches the server

The toast can only name the post if it knows the post's name, and it does not: a step
publishes a post id and nothing else, and the browser receiving the frame has not loaded that
post. The topic exists in one place on the path, and it is already being read. Both event
endpoints resolve the post row before they will send anything: the per-post one to answer 404,
the queue-wide one to answer "may this caller see it". `ownedByUser()` was selecting the
literal `1`.

So `pipelineEventStream()`'s second argument changed from a `matches` predicate returning a
boolean to a `select` function returning the payload to send, or `null` to send nothing. The
global feed's implementation now selects `posts.topic` instead of `1`, memoises the topic per
post for the life of the connection exactly as it memoised the yes/no, and returns
`{ ...payload, topic }`. The payload is spread first so a published `topic` cannot pass itself
off as the stored one. The per-post route does the same from the row its ownership check
already read, so both feeds put one shape on the wire.

Three consequences worth stating:

- A post renamed mid-connection keeps announcing itself under the topic it had when the first
  event for it arrived. The memo is what makes the feed one query per post rather than one per
  event, and a reconnect (any transport error, any page load) clears it.
- The frame is one field bigger for every subscriber, including the per-post one whose page
  already knows the topic. That is the price of one wire shape.
- `null` now means "send nothing" where `false` did. `stream.ts` fails closed on a `select`
  that throws, unchanged.

On the client: `describePost()` returns the topic or `undefined`, and sonner omits the
description entirely for `undefined`, so a frame without a topic says nothing rather than
guessing. A failure toast reads `<topic>: <reason>`, or whichever of the two it has.
`pipeline_complete` reads `<topic> is ready for export`, or `Ready for export`. The two
duplicate toasts on `/posts/[id]` are deleted; the refetch and the analytics refresh they sat
beside are not.

One more thing on those lines: the `View` action pointed at the post the reader is already
looking at, on the one page where both notifiers fired. It is now offered only when
`usePathname()` says the reader is somewhere else.

Batched with it, same class and same file: `handleRerun`'s toast said
`Re-running from write`, the last raw stage name on that page. It reads `Re-running from
Write` through `stageLabel()`.

### Root cause, one per site

**`Rerun Stage` does not re-run a stage.** `POST /api/posts/{id}/rerun` finds the first stage
`stage_status` does not call complete, resets it and everything downstream, and starts a full
pipeline. The per-stage retry beside a failed stage is a different endpoint
(`POST /run?stage=<stage>`) and a different button, and that one is already correctly named
`Re-run Edit`. Before this change the header carried `Rerun Stage` two inches from
`Re-run Edit` and they did different things. The DOM readout on the demo post:

```
before: ["Rerun Stage", "Force Restart", "Re-run Edit", ...]
after:  ["Resume from Edit", "Start Over", "Re-run Edit", ...]
```

`resumeStage()` in `src/lib/run-state.ts` derives the named stage the way the handler derives
it, including the fallback that makes "re-run" on a finished post re-run `ready`, so the label
cannot promise a stage the run does not begin at.

**`Force Restart` names the force, not the loss.** `POST /restart` clears all six content
columns plus `final_html_content` and `stage_logs`, then runs from `research`. Nothing about
that is recoverable and nothing on screen said so. It is now `Start Over` behind an
`AlertDialog` whose body names what is discarded (the six stage outputs and the run's token
and cost record) and what is kept (the post's settings and review gates). The dialog's own
text, read out of the live DOM:

> Start this post over? The run begins again at Research. Everything the pipeline has produced
> for this post is discarded first: the research notes, the outline, the draft, the edited
> copy, the images and the final article, along with this run's token and cost record. The
> post's own settings and review gates are kept. / Keep this run / Start over

**Three handlers swallowed the server's reason.** `handlePause`, `handleRerun` and
`handleRestart` were `catch { toast.error("Failed to pause") }` while every neighbour on the
same page (`handleRun`, `handleRetryStage`, `handlePublish`) went through `apiErrorMessage`.
A refusal with a reason attached reached the user as a generic failure. All three now use
`apiErrorMessage` with a fallback that names the action.

**`Internal Server Error` displaced every caller's fallback.** This is the upstream cause of
the whole class, and it is not on the page. `withServerError()` answers a throw nobody
anticipated with Starlette's wording and deliberately keeps the cause out of the body, so the
`detail` on a 500 names no complaint at all. `apiErrorMessage()` preferred it over the
caller's fallback anyway, so `apiErrorMessage(e, "The post could not be saved.")` printed
`Internal Server Error` instead. That is strictly less information *and* it is HTTP jargon.
It now falls back, using the constant imported from the module that writes it so the two
cannot drift. The reasoning was already written down one branch lower, in the comment about
non-JSON bodies: "Neither is worth showing to a user, so the caller's own wording wins."

**`Failed to decrypt WordPress app password (em dash) check WP_ENCRYPTION_KEY`** was copied
byte for byte from Python and reaches the profile's WordPress tab through all three
`/wordpress/*` endpoints. It names a server environment variable the reader can neither see
nor change, and the only thing that reaches that branch through the dashboard is a stored
token this deployment's key no longer opens. The fix a user can perform is to type the
application password in again, so that is what it now says. Python's wording stays in the
codebase as `PY_WP_DECRYPT_FAILED` and the parity oracle still records it; a `reworded()`
mapping in `wordpress.test.ts` is the one place the divergence is written down, applied to
both shapes an expectation can carry (a 400's `detail` and a 200 body's `error`), which is the
same mechanism P1.3a already established for the seven scenarios where the port stops
reproducing an uncaught Python exception.

**Three raw stage names, plus four more the sweep found.** `todo.md` named the
`stage-models-card.tsx` toasts (`write model saved`), its row-error fallback
(`Failed to save write`) and `/profiles/[id]`'s `aria-label={`${stage} stage mode`}`. The card
also labelled its model select, its effort select and its Revert button with the column value,
one line under a heading that already read `Write`. All seven now go through `STAGE_LABELS`.
Live DOM, `/settings`:


### What none of this proves

- The parity oracle is now read through a rewriting function. `reworded()` is derived from two
  named constants and returns anything it does not recognise untouched, so a scenario the
  export adds is still compared byte for byte, but the file is no longer a pure byte-for-byte
  comparison and a future divergence has to be added there deliberately. That is the same
  trade `divergentAnswer()` already made for P1.3a.
- The WordPress reword was verified against a Fernet token this deployment cannot open, not
  against a missing `WP_ENCRYPTION_KEY`. Python answered the same 400 for both and the port
  reproduces that, but only the first case was exercised in a browser. In the second case the
  advice the message gives ("enter it again") does not help, because the save would fail too;
  it would fail with its own message, which is an operator problem rather than this one.
- `Publishing not supported for output_format '<value>'` is still raw. It is reachable only
  through a race and it is P2.68's to fix, but it is a raw column name and a raw enum value in
  a user-facing string today.
- The four `aria-label` fixes are in the accessibility tree, not on the screen. They were
  changed because they are the same one-line `STAGE_LABELS` call as the visible sites in the
  same components, not as part of an accessibility sweep, which the objective puts out of
  scope.
- `Resume from Ready` on a post whose every stage is complete is the honest name for what the

## P3.4a

The three server-backed search boxes. One request per keystroke, and the oldest answer wins.

### Root cause

Every list here reads its filters straight into the effect that fetches it, so the fetch
callback's identity changes on every character typed:

| Surface | Fetch effect | Requests for a five-letter word |
| --- | --- | --- |
| `/` posts list | `useCallback(..., [statusFilter, profileFilter, search])` | 5 `GET /api/posts` **and** 5 `GET /api/profiles` |
| `/profiles/[id]?tab=links` | `useEffect(..., [loading, linksSearch, fetchLinks])` | 5 `GET /api/profiles/{id}/links` |
| `/monitor` logs tab | `useCallback(..., [level, stage, profileId, searchQuery, timePreset, page])` | 5 `GET /api/analytics/logs` |

Measured in Chrome, not inferred. The posts list is the worst of the three because its mount
effect fetches the profile filter's options beside the rows:

```
reqid=60 GET /api/posts?q=b      reqid=61 GET /api/profiles
reqid=62 GET /api/posts?q=br     reqid=63 GET /api/profiles
reqid=64 GET /api/posts?q=bre    reqid=65 GET /api/profiles
reqid=66 GET /api/posts?q=brea   reqid=67 GET /api/profiles
reqid=68 GET /api/posts?q=bread  reqid=69 GET /api/profiles
```

Ten requests for one typed word, nine of them already superseded when they answered. The
profile list was not found by reading the code; it was found by reading the network log, and
it is the "list that refetches everything on a single-row change" in this section's own words:
the options in that filter are a property of the account and cannot change because the rows
under them did.

Second defect, in the same three files: none of them checks that an answer is still the one
being waited for. `setPostList(data)` / `setLinks(data.items)` / `setData(result)` run
unconditionally after the await, so of two searches in flight the one that answers **last**
wins, regardless of which was asked for last. On a fast local server this is invisible; on a
slow connection it is rows that do not match the box.

Third, only on the logs tab: `useEffect(() => { setLoading(true); fetchLogs() }, [fetchLogs])`
swapped the whole table for eight skeleton bars on every keystroke, where the posts list had
already decided the opposite (a comment in `page.tsx` says skeletons are opt-in "because this
runs on every keystroke in the search box").

### What changed

Two hooks, because the same four lines would otherwise be written three times:

- `src/hooks/use-debounced-value.ts`: `useDebouncedValue(value, delayMs)` returns the value
  held back until it has stopped changing, with the first value not held back so a mount does
  not wait. `SEARCH_DEBOUNCE_MS = 300` lives beside it, one value for all three boxes.
- `src/hooks/use-latest-request.ts`: `useLatestRequest()` returns `begin()`, which starts a
  request and invalidates every earlier one; the handle it returns answers whether that
  request is still the newest. Every fetch asks before it writes anything, in `try`, in
  `catch`, and before it takes its own busy state down.

Each page now reads the raw value for what it shows the typist and the debounced one for what
it asks the server, and each records the query its rows actually came from:

- `/`: `shownFilter` (status only) became `shownQuery` (status, profile, search). `filtersActive`
  reads it rather than the live controls, because the empty state explains rows that are not
  there: a cleared search must not read as an empty account for the 300ms its replacement is in
  flight. The profile options moved to a mount-only effect.
- `/profiles/[id]`: new `shownLinksSearch` for the same reason ("No links match your search"
  versus "No internal links yet").
- `/monitor` logs tab: skeletons only when there is nothing on screen to keep. A filter change
  over existing rows spins the refresh control instead, which the component already had.

#### Root cause, which is one level up from the picker

`OUTPUT_FORMATS` in `src/lib/publishing.ts` offers three values: `markdown`, `wordpress`,
`nextjs`. `both` is not one of them, and Radix's `SelectValue` renders nothing when the
current value matches no `SelectItem`. So the picker was correct about what it can offer and
silent about what is stored.

`both` is there because it is the **column default**, on `website_profiles.output_format` and
on `posts.output_format`, carried over value-for-value from the Python schema. It names no
destination anything in this app handles: `POST /api/posts/{id}/publish` answers it with
`Publishing not supported for output_format 'both'` (todo P2.68) and the auto-publish hook
skips it the same way. A row holding it publishes nowhere and reads as nothing.

Both route validators materialise pydantic's `"markdown"` on every insert, so the column
default only lands on a row written by something other than those two handlers. The three
profiles here were seeded by SQL in earlier iterations, which is exactly that case, and is
why this was filed at P2.113 as reachable but unobserved. It is observed now.

#### The fix, in two parts

**The default.** `drizzle/0003_output_format_default.sql` moves both columns' default to
`markdown` and rewrites the rows that took the old one. That is behaviour-preserving:
`both` publishes nowhere today and `markdown` publishes nowhere, so what changes is only that
the value can be rendered and named. `src/db/schema.ts` follows. Four comments that explained
the pydantic/column disagreement for `output_format` now say the two agree and when they
stopped disagreeing.

**The picker.** The column is a bare `varchar(20)` with no check constraint, and both route
validators take `output_format` as `z.string()`, so an unoffered value is still reachable
through the API. The trigger now names it and a line under the field explains it:

```

  alert:   "\"both\" is not a format this app can produce. Pick one below and save."
```

The value is still not rewritten until the user picks one, which is the rule the rest of this
component already follows for a destination that is configured but unavailable.

### Root cause, one level up from the strip

`GET /api/queue` grouped on `posts.current_stage` and summed every group whose key is one of
the six stage names into `running`. That is the Python arithmetic, and it was preserved
deliberately at the port with a comment saying so. It is wrong as a description of a run
because `current_stage` records **where a run got to**, not what it is doing:

- A post created but never started carries `current_stage = 'research'` with an empty
  `stage_status`. The column says research; nothing has run.
- A post whose research stage threw carries `current_stage = 'research'` with
  `stage_status.research = 'failed'`. The column says research; the run is dead. Only
  `markPipelineFailed()` moves the column to `failed`, and it does not fire on every failure
  path, which is the same disagreement `deriveRunState()` was written for at P3.2.

So the two screens were reading two different columns. `deriveRunState()` in
`src/lib/run-state.ts` is the one thing in the repo that reads both and applies a precedence
between them, and it is what the badge column already used.

### The fix

`GET /api/queue` now selects `current_stage` and `stage_status` for every owned post, hands
each to `deriveRunState()`, and returns one count per `RunStateKind` plus a total. `QueueStatus`
becomes `Record<RunStateKind, number> & { total: number }`, and `RUN_STATE_KINDS` is exported
from `run-state.ts` so a kind added later without a bucket is a type error rather than a
silently missing line.

Two consequences of moving the arithmetic off the `GROUP BY`, both intended and both written
into the route's own comment:

- **`total` is now the sum of the buckets.** Python's `total` counted every group while five
  named buckets counted some of them, so a row with a null or out-of-enum `current_stage`
  landed in `total` and nowhere else. `deriveRunState()` answers for any column value, so
  every row now lands in exactly one bucket.
- **The handler reads two columns of every owned post** instead of a grouped count: a scan
  proportional to the account's history rather than to the number of distinct stages. That is
  the price of one vocabulary across the two screens. If it ever matters the answer is to
  cache the response, not to re-derive the precedence rules in SQL and keep two copies of them
  in step.

The strip reads those buckets through a `QUEUE_LINES` descriptor. `running` and `in_progress`
share the `Running` line, because the difference between them is about the record (a stage
recorded as running, versus a row caught between two of them) rather than about what the
reader is waiting for. `Finished with errors` is the only line that hides at zero: it is a
complaint, where the five above it are the standing shape of the queue.

The chart beside it also grouped on `current_stage`, and was titled `Posts by Status`, which
is the same word the strip's counts were claiming. It is a legitimate second question, so it
keeps its data and is renamed `Posts by Stage` with a description saying which question it
answers: "Where each post's row sits in the pipeline, not what its run is doing".

### Root cause and fix

The root layout is a server component, so a child layout cannot remove what it drew; the
overlay existed to paint over a decision made one level up. The decision moves to where it can
be made: `src/components/app-chrome.tsx`, a client component holding the frame the root layout
used to inline, which reads `usePathname()` and returns `children` alone on `/auth` and
`/auth/*`. `children` stays a server-rendered slot, so no route loses its server components,
and the gate runs during SSR too, which is why `<aside` is absent from the HTML `curl` gets.

`src/app/auth/layout.tsx` is deleted rather than rewritten. With the chrome gone it had nothing
left to do: `globals.css` puts `bg-background` on `body`, and the page's own
`main.flex.min-h-screen.items-center.justify-center` already centres the card and grows past
the viewport when the card is taller than it.

Taking the sidebar off those routes took the only thing on them that named the product, so
`src/app/auth/[path]/page.tsx` names it itself: the mark from `public/icon.svg` beside
`Content Crew` / `CONTENT ENGINE`, in the sidebar's own wording and type, above the card. The
image is `alt=""` because the text beside it is the name, and `priority` because it is the
only image on the first screen a visitor sees.

The prefix test is `pathname === "/auth" || pathname.startsWith("/auth/")`, not a bare
`startsWith("/auth")`, so a future `/authors` route is an app route.
