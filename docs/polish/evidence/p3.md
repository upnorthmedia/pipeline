## P3.1a

**The item.** P3.1 asks where each concern lives when settings, profiles and per-post
configuration overlap, with the reasoning written down. It is split three ways, and this is
the first child: the decision record, plus the surface the decision settles first,
`/posts/new`. It closes **P2.111** (`/posts/new` has no per-post pipeline configuration, so a
post created there silently takes the profile's gates with no indication that it did).

### The decision

Three owners, and each concern belongs to exactly one of them.

| Owner | Surface | What it owns | Why |
| --- | --- | --- | --- |
| Account | `/settings` | Provider API keys, per-stage model choice, `rules/*.md` | One set of credentials and one set of prompts for every site the account runs. Nothing here varies per site, so putting a copy on a profile would mean N places to rotate a key. |
| Site | `/profiles/[id]` | Identity (name, URL, niche, audience), voice (tone, word count, brand voice, avoid, required mentions), image style, publishing connections (WordPress, Next.js), sitemap and internal links, and the defaults new posts start from including `default_stage_settings` | Everything a destination needs to be written for and published to. Publishing is the case that forces this: both publish steps read their credentials off the linked profile, so the connection has to live where the link points. |
| Post | `/posts/new`, `/posts/[id]` | Topic, slug, intent, article type, keywords, competitor URLs, and per-run overrides of the site's writing values plus the WordPress category and author | The one article. Every value here starts as the site's and is then editable for this run only. |

Two rules fall out of that table, and `/posts/new` broke both.

1. **A value copied from another owner says where it came from.** Eight fields on the form
   (`niche`, `target_audience`, `tone`, `word_count`, `output_format`, `website_url`,
   `brand_voice`, `avoid`, `related_keywords`) are filled from the profile the moment one is
   picked, and are then plain editable inputs. Nothing said they were copies, and nothing said
   an edit was for this post rather than for the profile.
2. **A setting the post cannot own is shown, not hidden.** `stage_settings` decides which of
   the six stages parks the run in front of a reviewer. The post row carries it, but the value
   is the profile's: `applyProfilePrefill` in `src/app/api/posts/prefill.ts` copies
   `default_stage_settings` over it. The form never mentioned it, so a run that stopped at
   Outline stopped for a reason that had never appeared on any screen the user had been on.

### Why the gate card is read-only

`applyProfilePrefill` copies `default_stage_settings` onto the post whenever the submitted
`stage_settings` equals the schema default, which is six `auto`s:

```ts
if (equalsDefault(filled.stage_settings, POST_CREATE_DEFAULTS.stage_settings)) {
  // Copied without a null guard, so a profile that has none clears the post's.
  filled.stage_settings = profile.defaultStageSettings
}
```

So a per-post editor that let a user clear every gate would send six `auto`s and have the
profile's gates written straight back over them, with a 201 and no warning. "Clear one gate,
leave another" would survive; "clear them all", the case a user reaches for most, would not.
Until that rule changes, an editor here would be an edit the server discards. The honest
surface is one that says what the run will do and points at the profile where it is decided,
which is also what the ownership table says: gates are a site concern.

That prefill asymmetry is a real trap and is filed as a new `todo.md` entry rather than fixed
here, because changing it rewrites a rule the Python parity oracle in
`src/app/api/posts/create.test.ts` asserts.

### The two fallbacks, which disagree

`effectiveStageMode()` in `src/lib/stages.ts` is a function rather than an index because the
pipeline reads a missing value two different ways:

- A post whose whole `stage_settings` column is null runs every stage unattended:
  `post.stageSettings || defaultStageSettings()` in `src/mastra/post-state.ts`.
- A column that names *some* stages parks the run at the ones it leaves out:
  `DEFAULT_GATE_MODE` in `src/mastra/steps/stage-io.ts` is `"review"`, because Python read the
  column with `.get(stage, "review")` and failed safe towards the human.

So a profile row holding `{"research": "auto"}` stops the run at the five stages it does not
name. A card that assumed `auto` for an absent key would show a run that never stops and then
stop it. `stage-modes.test.ts` cross-checks both constants against the step module.

### Two decisions worth the words

**One form, three tabs, and a save bar bound by id.** Every field on the page is React state,
not an uncontrolled input, so a tab the user has left keeps its edits: `handleSave` reads the
state, not the DOM. The three settings tabs are `TabsContent` inside one `<form
id="profile-form">`; the links tab sits outside it, because the Add Link form is a form of its
own and nesting forms is invalid. The save bar is therefore outside the form too, bound with
`<Button type="submit" form={PROFILE_FORM_ID}>`, and sticky at the bottom of the viewport. That
is what makes `Re-crawl Schedule`, a profile column that lives in the crawl card, savable from
the tab it is on. Proven in the browser rather than only in jsdom: on the Internal links tab,
`Re-crawl Schedule` switched Weekly to Monthly, `Save Profile` clicked, toast `Profile saved`,
and then

```
GET /api/profiles/554c0d27-...  ->  {'name': 'Gated Blog', 'recrawl_interval': 'monthly', ...}
```

Native `required` validation no longer fires on that button, which is the correct trade here
and not a regression: with tabs, a required field on an unmounted tab does not exist to
validate, and `handleSave`'s own check ("Name and Website URL are required") is what actually
guards the submit. That check has a test older than this change.

**`?tab=` read with the History API, not `useSearchParams`.** The tab is read once on mount
from `window.location.search` and written back with `history.replaceState`. `useSearchParams`
would be the idiomatic reader, but it puts a Suspense-boundary requirement on any client page
Next may prerender, and this page renders nothing on the server anyway; `router.replace` would
cost an RSC round trip per tab click on a page that fetches everything itself. An unknown or
missing value opens `Site` rather than an empty page. The payoff is a linkable tab, and
`pipeline-gates-card.tsx` now spends it: `Edit gates in the <name> profile` points at
`/profiles/<id>?tab=defaults`, three cards down the third tab, rather than the top of the page.

## P3.2a

The first child of P3.2, and the one that has to come first: before the pipeline's state can
be readable at a glance, the one line every surface already shows about a run has to be true.
It was not. Closes `todo.md` finding P2.106.

### The defect

`markPipelineComplete()` in `web/src/mastra/post-state.ts` is unconditional, and its docblock
says why: Python's `_post_completion_hook` stamped `current_stage = "complete"` and
`completed_at` at the end of a full run without consulting `stage_status`, and the `images`
stage writes `images: failed` and *returns* rather than raising, so the chain carries on to
`ready` and ends normally. A run that produced no pictures is therefore stamped exactly like
one that produced six.

Both surfaces that summarise a run read `current_stage` alone:

- `web/src/app/page.tsx:413` and `web/src/app/posts/[id]/page.tsx:450` rendered
  `<StageBadge stage={post.current_stage} />`, and `StageBadge` printed the column's raw enum
  value uppercased in a monospace pill.

So the posts list said `COMPLETE` for a post whose own progress bar, three columns to the
right, painted a red dot, and the post page said `COMPLETE` above a run trace whose Images row
said `Failed` with the Gemini quota error underneath it. `docs/polish/ui/p32a-before-list.png`
and `p32a-before-detail.png` are that state in a real browser.

The post page also had no failure affordance at all for a stage. It has one for a failed
*publish* (`publishFailure`, added at P1.3) and one for a failed refetch, but a stage that
failed inside the run appeared only as a red dot and a red row in the trace, with no retry
next to either.

### Where the fix belongs, and where it does not

Not on the write. `markPipelineComplete()` is the run's own record of what it did and it is
accurate: the run *did* reach the end. What was wrong is that one of the two columns that
together hold the answer was being reported as the whole state. So the fix is a derivation,
`deriveRunState()` in `web/src/lib/run-state.ts`, and it is the only thing the UI asks.

**Precedence**, which is the whole content of the module and took one browser check to get
right:

| Order | Condition | Label |
| --- | --- | --- |
| 1 | `current_stage === "failed"` | `Failed` / `Failed at <Stage>` |
| 2 | `current_stage === "paused"` | `Paused` |
| 3 | a stage is `running` | `Running <Stage>` |
| 4 | a stage is `review` | `Waiting for you` |
| 5 | a stage `failed` and `current_stage === "complete"` | `Finished with errors` |
| 6 | a stage `failed` | `Failed at <Stage>` |
| 7 | `current_stage === "complete"` | `Complete` |
| 8 | no stage has moved off `pending` | `Not started` |
| 9 | anything else | the row's own stage name |

Rows 1 and 2 are above the stage map rather than below it, and that ordering is a correction
made *after* the first browser pass, not a guess. Shooting the live posts list with the map
read first showed `E2E Post Editor Topic`, a row holding `current_stage = "failed"` and
`stage_status = {"research": "running"}`, reading `Running Research`. It is not running:
`markPipelineFailed()` writes the terminal stamp without touching `stage_status`, so the
stage that threw stays `running` in the map for good. The pause endpoint has the same shape,
documented in its own route file: it "overwrites `current_stage` and nothing else", so a

`failedStages` is populated whatever `kind` comes out, so a run still executing reads
`Running Ready` in the badge while the failure banner for the earlier stage stays on screen.

## P3.2b-i

The gate queue. `todo.md` finding P2.98: nothing in the app lists the posts waiting at a
review gate, so a parked run is findable only by opening the post it belongs to, which means
an operator has to already know which post is blocked. Closes P2.98.

### Why no existing filter could answer it

The posts list already had a state filter, and every one of its five values goes to the
server as `status`, which `GET /api/posts` applies as `eq(posts.currentStage, ...)`. That
column cannot answer this question. `markStageForReview()` in `web/src/mastra/post-state.ts`
writes the gate to `stage_status[stage] = "review"` and sets `current_stage` to the stage it
suspended in, so a post waiting on a person carries exactly the same `current_stage` as one
waiting on a provider. `GET /api/queue` has the same blind spot and says so in its own
docblock: "a post parked at a review gate still counts as running".

`deriveRunState()` (P3.2a) already reads both columns and already labels the row
`Waiting for you`, so the state was legible once you were looking at the post. Nothing let
you ask for it.

### What changed

- `GET /api/posts` gains `awaiting_review=true`, the one parameter FastAPI never declared.
  It is an `OR` of six jsonb containment tests, one per pipeline stage:
  `stage_status @> '{"outline":"review"}'::jsonb`. Per stage key rather than one test over

  turns it on, so `awaiting_review=` or `=0` leaves the list as it was rather than emptying

- `/` gains `Waiting for review` as the second entry in the state filter, above the four

  option could not be reached from a test.
- The header count and the empty state describe the queue when the queue is what is on

## P3.2b-ii

The publish leg of the run trace. `todo.md` finding P2.108: the trace is the view built for
watching a run, and it ended at `ready`. A publish is the last thing a run does and the thing
most likely to fail on something outside this app, and the trace said nothing about it, in
either direction. Closes P2.108.

### The defect, and that it has two halves

`RunTrace` builds its table from `STAGES`, the six pipeline stages, and `buildRunTrace()`
drops every `execution_logs` entry whose `stage` is not one of them. Both publish steps write
`stage: ""`:

```
$ git show HEAD:web/src/mastra/steps/wordpress-publish.ts | grep -n 'stage: ""'
109:    stage: "",
238:        stage: "",
$ git show HEAD:web/src/mastra/steps/nextjs-publish.ts | grep -n 'stage: ""'
140:    stage: "",
```

So the reading side had no publish row at all. The writing side was thinner than the finding
says, which the grep above is the evidence for: three entries between the two steps, all of
them terminal. Neither step wrote a `publish_start` entry (both announced the start on the
bus only, and an SSE frame is gone the moment it is delivered), and `nextjs-publish.ts` wrote
nothing at all on success. A Next.js publish therefore left one durable trace of having
happened, `nextjs_published_at`, and a WordPress publish left one line with no start time in
front of it, so nothing could say how long a publish took or show one in flight.

### What changed

**The steps.** `wordpress-publish.ts` and `nextjs-publish.ts` each append a `publish_start`
entry after moving the row to `publishing` and before announcing it on the bus, which is the
row-then-trail-then-bus order both `_fail` paths already used and for the same reason: a
dashboard that refetches on the event must not read a row that has not recorded the fact yet.
`nextjs-publish.ts` gains the `publish_complete` entry it never wrote. Every publish entry now
carries `data: { target: "wordpress" | "nextjs" }`.

Both are deliberate divergences from the Python steps, on top of the failure-path divergence
the port already made for the same reason. The test that asserted `writes no execution log
entry` is replaced rather than adjusted: the behaviour it pinned is the defect.

**`data.target`, and why the message prefixes still matter.** Nothing clears the other
destination's status column, so one row can carry entries from both. Historic rows have no
`data.target`, and the only thing on them that names a destination is the message prefix the
steps already wrote (`WordPress publish failed: `, `Next.js publish failed: `,
`Published to WordPress: `). `publish-report.ts` owned two of those three as a private list;
it now owns all four as one table and exports `publishTargetOfMessage()` beside the
`publishFailureReason()` its own `lastPublishError()` was inlining. An entry that names no
destination either way is taken as the leg on screen, since it is the only account there is.

**The trace.** `buildRunTrace()` takes an optional `publish: { target, status }` and returns a
`PublishTrace | null` beside `stages`. The status comes off the row's `wp_publish_status` /
`nextjs_publish_status` column, mapped onto the stage vocabulary (`publishing` -> `running`,
`published` -> `complete`), for the same reason `stage_status` decides a stage's status: the
column is the pipeline's own record and the log is the audit trail behind it. The log supplies
what the column cannot say, which is when it started, how long it took and what went wrong.

Two rules keep it from asserting things it does not know:

- an attempt is only attributed to the destination on screen, so a post that changed format
  does not have the old destination's timing shown against the new one;
- the reason is carried only when the failure is the last publish entry on the row, because a
  retry that succeeded leaves the earlier failure's entry in place forever (the same rule
  `lastPublishError()` documents for the header banner).

Wall clock across the two entries is the duration, since no step measures a publish. It is
deliberately not added to the header's total time, tokens or cost: those are stage
measurements, a publish runs no agent, and a run total that silently included network time
would disagree with the analytics endpoints.

**The page.** `/posts/[id]` passes the column it already read for the failure banner. The
destination is `publishTargetOf(post.output_format)`, the same rule the banner uses, so a post
whose format is `both` or `markdown` shows no publish row: `both` is the column default that
no publish step handles, which is `todo.md` P2.113 and not this item.
