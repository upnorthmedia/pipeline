# P4 evidence

Section P4 is the tail of Done criterion 9: the `[confirmed]` entries left in `todo.md` that
affect correctness, data integrity or something a user can see.

## P4.1

`POST /api/queue/pause-all` scoped to the run states Pause All claims to act on.

### The cause, read off the code

`pause-all/route.ts` selected on `current_stage` alone:

```ts
const PAUSABLE: string[] = ["pending", ...STAGES]
...
.where(and(eq(websiteProfiles.userId, user.id), inArray(posts.currentStage, PAUSABLE)))
```

Three different run states sit on a stage name, and that predicate cannot tell them apart:

| Row | `current_stage` | `stage_status` | `deriveRunState()` |
| --- | --- | --- | --- |
| a stage in flight | `write` | `{write: "running"}` | `running` |
| parked at a review gate | `write` | `{write: "review"}` | `review` |
| died at a stage | `research` | `{research: "failed"}` | `failed` |

`markStageForReview()` in `src/mastra/post-state.ts:263` writes
`currentStage: currentStageUnlessPaused(stage)`, which is why the parked row is inside the
guard, and `recordRunFailure` leaves `current_stage` on the stage that threw.

Pausing either of the last two overwrites the only column that said so:
`deriveRunState()` gives `current_stage === "paused"` precedence over the stage map, so both
report as `Paused` afterwards.

The review case is worse than a mislabel. `POST /api/queue/resume-all` enqueues the
single-stage form, and a named stage skips its review gate by design, which
`queue-control.test.ts` already pinned before this item
(`"enqueues the single-stage form, so the resumed stage skips its review gate"`). So
pause-all followed by resume-all ran the stage the reviewer never approved.

### The fix

`PAUSABLE_RUN_STATES` in `src/lib/run-state.ts` is `["running", "in_progress", "not_started"]`,
and the handler keeps Python's column guard on top of it. Two guards, doing two things:

- the column guard bounds the write to rows a run actually placed somewhere, so a null or
  unrecognised `current_stage` is still left alone by a bulk control;
- the state guard, read through `deriveRunState()`, drops the runs waiting on a person and
  the runs that are already dead.

`not_started` stays in, deliberately. `POST /api/posts/{id}/restart` and `.../rerun` both
write `currentStage: "pending"` and then enqueue, so a run that is about to spend money reads
`pending` with an empty `stage_status` until its first stage marks itself running, which is
exactly `not_started`. The two columns cannot tell that run from one nobody ever started, and
failing to pause the first is the worse of the two mistakes. `pauseGate()` stops it in front
of `research`.

The write set is a strict subset of what it was, so no existing assertion in the file needed
editing. One assertion elsewhere did: `"resume all calls queue.resumeAll"` in
`QueueMonitor.test.tsx` now seeds a paused run, because Resume All is disabled when nothing is
paused and the click was no longer a click.

### What none of this proves

- Resume All was not pressed in the browser. Doing so would put real `workflow.start` events
  on the shared Redis bus for seven posts; the round trip is covered by the real-database
  test instead.
- The `not_started` decision is a judgement, not a measurement. A run enqueued and not yet
  started is indistinguishable from one nobody started, so Pause All still relabels a
  never-started post as Paused. The alternative loses a pause on a run that is about to bill.
- Nothing here changes `POST /api/posts/{id}/pause`. The per-post button still pauses whatever
  the reader pressed it on, including a parked or dead run, which is a deliberate difference:
  the reader chose that row.
- The counts on the buttons come from `GET /api/queue`, which the page polls every ten
  seconds, so a button can name a stale number for up to that long. The handler re-derives at
  request time, so the write is right even when the label is not.
- No worker was running during the browser pass, so no stage was genuinely mid-flight; the
  `running` rows are seeded `stage_status` values.

## P4.2

`GET /api/analytics/dashboard` counted a completion the way Python did, off
`current_stage` alone, so a run that reached the end with a failed stage was a
completion. `markPipelineComplete()` is unconditional by design, which is the
whole reason `deriveRunState()` exists, and the monitor page printed both
numbers on one screen.

### The defect, live

The 15-post account from P4.1, dev server on :3000, session minted straight into
`auth_sessions`:

```
$ node --env-file=.env /tmp/p42-scan.mjs
user_id                            posts  col_complete  with_failed
HeJdC1M5STXEa7s5rc4k8KUMmHxmwAwp   15     4             1
```

`/monitor`, overview tab, before:

```
TOTAL POSTS 15   COMPLETION RATE 26.7%   AVG DURATION --   POSTS TODAY 0
...
Queue Controls
Running: 5  Waiting for you: 2  Not started: 2  Paused: 0  Failed: 2  Finished with errors: 1
```

26.7% is 4 of 15. The strip below it accounts for 12 of the 15 rows and leaves
three unlisted, because it has no Complete line: three runs finished, not four.
The fourth is the `Finished with errors: 1`. `ui/p4b-completion-rate-before.png`.

### Failing first

`web/src/app/api/analytics/dashboard.test.ts`, three new cases against the real
database, run before the route was touched:

```
$ pnpm vitest run src/app/api/analytics/dashboard.test.ts -t "by_status and the totals"
 ✓ buckets by current_stage and sums every group into total
 ✓ counts a null current_stage under the "null" key, as json.dumps did
 ✓ rounds completion_rate half to even, not half up
 ✓ reports a completion rate of 0 rather than dividing by zero
 × leaves a run that reached the end with a failed stage out of complete
 ✓ counts a complete row with no stage_status, which every legacy row is
 ✓ counts a stage the row never left as incomplete, whatever the column says

 FAIL ... leaves a run that reached the end with a failed stage out of complete
 AssertionError: expected 4 to be 3
```

The two that pass throughout are the anti-vacuity half and they are the reason
the fix is not simply "subtract the failures": a `complete` row with an *empty*
`stage_status`, which every row written before the column existed is, still has
to count, and a row stamped `failed` over a stage still recorded as `running`
still must not. Neither column answers alone, which is why the route now hands
both to `deriveRunState()` rather than filtering in SQL.

The UI half, on `QueueMonitor.test.tsx`, before the caption was added:

```
$ pnpm vitest run src/app/monitor/QueueMonitor.test.tsx -t "completion rate"
 FAIL  MonitorPage > names the two counts behind the completion rate
 Unable to find an element with the text: 42 of 50 runs finished cleanly
```

### The change

- `src/app/api/analytics/dashboard/route.ts` reads `current_stage` *and*
  `stage_status` for every owned post instead of a grouped count, buckets
  `by_status` on the column as before, and counts `complete` by
  `deriveRunState(...).kind === "complete"`. `total` is now the row count, which
  is the same number the sum of the groups was.
- `by_status` is deliberately still the column. It is what the "Posts by Stage"
  chart draws and what its description already says it draws, "where each
  post's row sits in the pipeline, not what its run is doing", and making it a
  second copy of the run-state buckets would duplicate the Queue Controls strip
  four inches below it. The split is stated in the route's header comment so
  the next reader does not treat the two `complete`s as a bug.
- The Completion Rate card prints its two counts under the percentage, because
  a bare percentage cannot be checked against anything else on the screen.

### What none of this proves

- The bar chart's `Complete` bucket and the strip's `Complete` count still
  differ by design on this account (4 rows, 3 runs). The card's caption is what
  reconciles them; nothing forces a reader to read it.
- Nothing was measured about the cost of the row scan that replaced the grouped
  count. It is the same scan `GET /api/queue` already does on every poll of this
  page, so the page went from one scan to two, on an account of 15 posts.
- `avg_duration_s` still averages `completed_at - created_at` over every row
  that has a `completed_at`, including the runs that finished with errors. That
  is unchanged and arguably right, since the run did take that long.
- No run was executed. The four `complete` rows are the ones the account
  already carried; the derivation is proven on seeded rows in the test file.
