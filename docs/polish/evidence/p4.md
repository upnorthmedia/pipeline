## P4.1

`POST /api/queue/pause-all` scoped to the run states Pause All claims to act on.

### The cause, read off the code

`pause-all/route.ts` selected on `current_stage` alone:

```ts
const PAUSABLE: string[] = ["pending", ...STAGES]
...
.where(and(eq(websiteProfiles.userId, user.id), inArray(posts.currentStage, PAUSABLE)))
```

Three different run states sit on a stage name, and that predicate cannot tell them apart:

| Row | `current_stage` | `stage_status` | `deriveRunState()` |
| --- | --- | --- | --- |
| a stage in flight | `write` | `{write: "running"}` | `running` |
| parked at a review gate | `write` | `{write: "review"}` | `review` |
| died at a stage | `research` | `{research: "failed"}` | `failed` |

`markStageForReview()` in `src/mastra/post-state.ts:263` writes
`currentStage: currentStageUnlessPaused(stage)`, which is why the parked row is inside the
guard, and `recordRunFailure` leaves `current_stage` on the stage that threw.

Pausing either of the last two overwrites the only column that said so:
`deriveRunState()` gives `current_stage === "paused"` precedence over the stage map, so both
report as `Paused` afterwards.

The review case is worse than a mislabel. `POST /api/queue/resume-all` enqueues the
single-stage form, and a named stage skips its review gate by design, which
`queue-control.test.ts` already pinned before this item
(`"enqueues the single-stage form, so the resumed stage skips its review gate"`). So
pause-all followed by resume-all ran the stage the reviewer never approved.

### The fix

`PAUSABLE_RUN_STATES` in `src/lib/run-state.ts` is `["running", "in_progress", "not_started"]`,
and the handler keeps Python's column guard on top of it. Two guards, doing two things:

- the column guard bounds the write to rows a run actually placed somewhere, so a null or
  unrecognised `current_stage` is still left alone by a bulk control;
- the state guard, read through `deriveRunState()`, drops the runs waiting on a person and
  the runs that are already dead.

`not_started` stays in, deliberately. `POST /api/posts/{id}/restart` and `.../rerun` both
write `currentStage: "pending"` and then enqueue, so a run that is about to spend money reads
`pending` with an empty `stage_status` until its first stage marks itself running, which is
exactly `not_started`. The two columns cannot tell that run from one nobody ever started, and
failing to pause the first is the worse of the two mistakes. `pauseGate()` stops it in front
of `research`.

The write set is a strict subset of what it was, so no existing assertion in the file needed
editing. One assertion elsewhere did: `"resume all calls queue.resumeAll"` in
`QueueMonitor.test.tsx` now seeds a paused run, because Resume All is disabled when nothing is
paused and the click was no longer a click.

### What none of this proves

- Resume All was not pressed in the browser. Doing so would put real `workflow.start` events
  on the shared Redis bus for seven posts; the round trip is covered by the real-database
  test instead.
- The `not_started` decision is a judgement, not a measurement. A run enqueued and not yet
  started is indistinguishable from one nobody started, so Pause All still relabels a
  never-started post as Paused. The alternative loses a pause on a run that is about to bill.
- Nothing here changes `POST /api/posts/{id}/pause`. The per-post button still pauses whatever
  the reader pressed it on, including a parked or dead run, which is a deliberate difference:
  the reader chose that row.
- The counts on the buttons come from `GET /api/queue`, which the page polls every ten
  seconds, so a button can name a stale number for up to that long. The handler re-derives at
  request time, so the write is right even when the label is not.
- No worker was running during the browser pass, so no stage was genuinely mid-flight; the
  `running` rows are seeded `stage_status` values.
