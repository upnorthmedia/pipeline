## P4.1

`POST /api/queue/pause-all` scoped to the run states Pause All claims to act on.

### The cause, read off the code

`pause-all/route.ts` selected on `current_stage` alone:

```ts
const PAUSABLE: string[] = ["pending", ...STAGES]
...
.where(and(eq(websiteProfiles.userId, user.id), inArray(posts.currentStage, PAUSABLE)))
```

Three different run states sit on a stage name, and that predicate cannot tell them apart:

| Row | `current_stage` | `stage_status` | `deriveRunState()` |
| --- | --- | --- | --- |
| a stage in flight | `write` | `{write: "running"}` | `running` |
| parked at a review gate | `write` | `{write: "review"}` | `review` |
| died at a stage | `research` | `{research: "failed"}` | `failed` |

`markStageForReview()` in `src/mastra/post-state.ts:263` writes
`currentStage: currentStageUnlessPaused(stage)`, which is why the parked row is inside the
guard, and `recordRunFailure` leaves `current_stage` on the stage that threw.

Pausing either of the last two overwrites the only column that said so:
`deriveRunState()` gives `current_stage === "paused"` precedence over the stage map, so both
report as `Paused` afterwards.

The review case is worse than a mislabel. `POST /api/queue/resume-all` enqueues the
single-stage form, and a named stage skips its review gate by design, which
`queue-control.test.ts` already pinned before this item
(`"enqueues the single-stage form, so the resumed stage skips its review gate"`). So
pause-all followed by resume-all ran the stage the reviewer never approved.

### The fix

`PAUSABLE_RUN_STATES` in `src/lib/run-state.ts` is `["running", "in_progress", "not_started"]`,
and the handler keeps Python's column guard on top of it. Two guards, doing two things:

- the column guard bounds the write to rows a run actually placed somewhere, so a null or
  unrecognised `current_stage` is still left alone by a bulk control;
- the state guard, read through `deriveRunState()`, drops the runs waiting on a person and
  the runs that are already dead.

`not_started` stays in, deliberately. `POST /api/posts/{id}/restart` and `.../rerun` both
write `currentStage: "pending"` and then enqueue, so a run that is about to spend money reads
`pending` with an empty `stage_status` until its first stage marks itself running, which is
exactly `not_started`. The two columns cannot tell that run from one nobody ever started, and
failing to pause the first is the worse of the two mistakes. `pauseGate()` stops it in front
of `research`.

The write set is a strict subset of what it was, so no existing assertion in the file needed
editing. One assertion elsewhere did: `"resume all calls queue.resumeAll"` in
`QueueMonitor.test.tsx` now seeds a paused run, because Resume All is disabled when nothing is
paused and the click was no longer a click.

## P4.3

`web/src/lib/publish-report.ts`, `web/src/app/posts/[id]/page.tsx`.

### The cause, and the half of the ledger entry that was wrong

The first half holds, read off the code:

- `steps/wordpress-publish.ts:227` writes `wp_publish_status = 'publishing'`
  before it touches the destination, and the only writes that move it again are
  in the same step body (`published` at the end, `failed` from `fail()`).
  `steps/nextjs-publish.ts` has the same shape.
- `appendExecutionLog()` and both of those writes leave `updated_at` alone, so
  no other column moves either.

So a worker killed between those two points leaves the row on `publishing` with
nothing left in the process that owns it. On the page that reads as
`Publishing...` beside a spinner, forever, and the header's Publish button is
gated on `null` or `pending`, so the row had **no control on the page at all**:
no retry, no explanation, nothing to press.

The second half of the entry, `the publish workflows declare no retryConfig, so
no XAUTOCLAIM recovers one`, is wrong twice:

```
$ grep -n retryConfig src/mastra/workflows/wordpress-publish.ts src/mastra/workflows/nextjs-publish.ts
wordpress-publish.ts:36:  retryConfig: { attempts: MAX_ATTEMPTS - 1 },
nextjs-publish.ts:32:  retryConfig: { attempts: MAX_ATTEMPTS - 1 },
```

Both declare one, and in any case `retryConfig` is not what `XAUTOCLAIM` keys
off. The reclaim loop is `RedisStreamsPubSub`'s own, documented in this repo at
`workflows/reclaim-duplication.test.ts`: every `reclaimIntervalMs` it runs
`XAUTOCLAIM <stream> <group> <consumer> <reclaimIdleMs> 0-0` and delivers what
it claims, regardless of the workflow's retry policy. `RECLAIM_IDLE_MS` in
`src/mastra/index.ts` is 15 minutes.

That is what makes the honest statement a window rather than a verdict. Inside
15 minutes a quiet publish may still be running, or about to be re-delivered to
a live worker that finishes it. Past 15 minutes either no worker is alive to
reclaim it or the reclaimed copy went quiet too, and in both cases nothing is
going to move the row without the reader. `PUBLISH_STALL_AFTER_MS` is therefore
`RECLAIM_IDLE_MS`, and `src/lib/publish-stall-window.test.ts` fails if the two
drift apart:

```
$ # with PUBLISH_STALL_AFTER_MS bumped to 20 minutes
AssertionError: expected 900000 to be 1200000 // Object.is equality
```

### The clock

`publishStall()` measures from the later of two instants, both of them the
server's own:

- `updated_at`, which the publish route and `auto-publish.ts` stamp when the
  publish is asked for, and which nothing in the publish moves afterwards;
- the `ts` of the last `publish_start` entry, which the step writes when a
  worker has the post in hand.

Taking the later of the two is what gives a worker that picked the post up ten
minutes after it was queued its own full window rather than the remainder of
the queue's, and comparing them is what tells the two faults apart: a pickup
older than the request belongs to an earlier attempt, so the row was never
picked up for *this* one.

### What none of this proves

- No worker was killed mid-publish. The state a killed worker leaves is written
  into Postgres by hand, which is exactly the two columns and the one log entry
  the step would have left, but whether `XAUTOCLAIM` actually re-delivers a
  publish step to a restarted worker is read out of `reclaim-duplication.test.ts`
  and the transport source rather than watched.
- A retry after a WordPress publish died mid-flight can create a **second** post
  on the site. `wp_post_id` is written only after `createPost` returns, so an
  attempt that died between the request and that write leaves the row with no
  id, and the retry takes the `createPost` branch again. Filed in `todo.md` as
  `[investigate]`; the banner does not warn about it.
- Only the post page learned about this. The posts list, `/monitor` and the run
  trace's `Publish to <target>` row still show a stalled publish as in flight,
  and the trace's elapsed clock still counts up indefinitely.
- 15 minutes is the transport's window, not a measurement of how long a real
  WordPress publish takes. No publish has ever been timed against a real site in
  this repo, so a site slow enough to hold a step open past the window would be
  called stalled while it was still working. The retry is idempotent for a post
  that already has a `wp_post_id`, which is the case that survives.
- The tick is a 30 second `setInterval` while a publish is in flight. It is
  proven under fake timers on a mounted page, not on a tab left open for a real
  quarter of an hour.

## P4.4a

`web/src/mastra/announce-pause.ts`, `web/src/app/api/posts/[id]/pause/route.ts`,
`web/src/app/api/queue/pause-all/route.ts`, `web/src/hooks/use-sse.ts`,
`web/src/app/posts/[id]/page.tsx`,
`web/src/app/monitor/_components/overview-tab.tsx`.

P4.4 as filed held two findings. This is the first: a pause reaches no reader
but the one that pressed it. The second (a pause during `ready` leaves all six
stages complete, `current_stage = "paused"` and no `completed_at`, so the run
reads as unfinished) is split out as P4.4b and is untouched here.

### The cause

Every pipeline control on a post writes a column and then starts a run, and the
first thing the run does is publish `stage_start`, which every open reader
refetches on. The pause is the exception, and its own route header says so:

```
$ grep -n "enqueues nothing" src/app/api/posts/[id]/pause/route.ts
23: * It is also the one pipeline-control endpoint that enqueues nothing, which is
```

So `current_stage = "paused"` was committed with nobody told. `handlePause()` on
`/posts/[id]` calls `fetchPost()` straight after the request, which is why the
tab that pressed the button looked correct and hid this. Any other reader (a
second tab, the same post open on another machine, `/monitor` between two of its
ten-second polls, the button on the queue strip acting on eleven rows at once)
kept the run on screen as running.

`pauseGate()` in `steps/stage-io.ts` does publish, but it publishes a `log`
frame at the moment the *worker* stops, which is a different fact at a later
time: the page appends `log` to the debug panel and does not refetch on it, and
the monitor deliberately excludes `log` from `AGGREGATE_EVENTS`. Neither is
wrong; neither says the row changed.

Both route cases assert on a frame read back off the **real** Redis Streams
topic through a second `RedisStreamsPubSub` client subscribed without a `group`,
which is the same fan-out the SSE endpoint uses: a frame that arrives provably
crossed the transport the `web` / `worker` split depends on.

Two of the four cases pass throughout and are the anti-vacuity half. `announces
nothing for a post the caller may not pause` waits 500ms after the 404 and finds
no frame for that row, and `ignores a pause announced for a different post`
proves the page's new refetch is still filtered by post id.

### The fix

`announceRunPaused(postIds)` publishes one `run_paused` frame per row the write
actually moved, after the commit, from the `web` process. It carries no stage,
because there is no honest one to carry: the pause overwrites `current_stage`
and the stage that was in flight is still finishing. A publish that throws is
logged and swallowed, since the row is the authority and answering a pause with
a 500 because Redis was unreachable would tell the operator the run was not
stopped when it was.

On `pause-all` the frames go out for the rows that passed both guards only, so a
reader does not refetch a post the call left alone (P4.1 narrowed that set).

Three readers change. `use-sse.ts` gains the name: `EventSource` delivers a
frame carrying an `event:` field only to a listener registered for that exact
name, so a name missing from `NAMED_EVENTS` is received and discarded.
`/posts/[id]` refetches on it, beside `stage_review` and for the same reason.
The monitor's `AGGREGATE_EVENTS` gains it, because both aggregates behind that
tab group over `current_stage` and this is the only frame that accompanies a
write to it outside a run.

## P4.5

### The fix, and why the release needs no writer of its own

`reviewGate()` now appends `{ stage, level: "info", event: "stage_review",
message, data: { mode } }` between the row write and the publish, the position
`announceStageStart()` puts its own entry in and for the same reason: the audit
line a browser goes looking for after the frame is already on the row when the
frame lands.

Nothing writes a release entry to match it, and nothing needs to. The only way
out of a gate is through it, so the stage's own `stage_start` **is** the
release, and `buildRunTrace()` closes the wait on it. That keeps the writer to
one line of new behaviour and puts the arithmetic in the reader, where the
module's existing doctrine already lives.

`StageTrace` gains `review: TraceReview | null` (`at`, `releasedAt`,
`waitedS`). Two cases the derivation has to separate, both tested:

- An **engine retry** is the same attempt one failure later. `restartStage()`
  already keeps the retry history on it (`lastEventFor.get(stage) === "retry"`),
  and the wait is kept on the same signal.
- **The rerun button** names its stages, and a named run never gates
  (`stageNeedsReview()` returns false when `input.stages` is set). Carrying the
  old wait onto it would put a four minute review against an attempt nobody
  reviewed, which is the argument `restartStage()` already makes about the
  previous attempt's numbers. The wait is dropped.

The trace reports the wait only once it is over. While the run is parked, the
status column says `Awaiting review` and the release control sits under it; an
elapsed clock there would freeze, because the ticker on that card runs only
while something is executing, and a second forever-counting clock is the defect
P4.9 was filed about.

reachable by joining `website_profiles` through `profile_id`, and every read
handler inner-joins it (`src/app/api/posts/params.ts` says so in a comment, and
five test files already pinned the 404 it produces). A post with no profile
therefore belongs to nobody. It cannot be listed, opened, run or deleted
through the app, and nothing in the app can work out who wrote it.

### The test that was changed rather than added

`orphans the profile's posts and deletes its internal links` asserted the
defect as the contract: it deleted a profile with one post, expected 204, and
expected `kept.profileId` to be null. That behaviour is what this item is
about, so the case was replaced, not repaired around: one half became
`deletes the profile's internal links with it` (unchanged behaviour, no post
involved) and the other became the refusal above. The old assertion is quoted
here so the change is on the record rather than buried in a diff.

### The decision

Three options were real. Cascade-deleting the posts with the profile is what
most apps do and what the row menu's single unconfirmed click implies, and it
is the one that silently destroys content. A migration that nulls, archives or
deletes the existing orphans has to decide the fate of rows whose owner cannot
be determined, from a process that cannot ask anybody. Refusing the delete is
the only one of the three that writes nothing it cannot justify.

So `DELETE /api/profiles/{id}` answers 409 when the profile still has posts,
counting them inside the same transaction as the delete so a post created while
the request is in flight cannot be stranded by it:

```
withOne:  409 {"detail":"This profile still has 1 post. Delete it before deleting the profile."}
withNone: 204
```

and the dashboard says so. `handleDelete()` threw the server's sentence away
and printed `Failed to delete profile`; it now relays it through
`apiErrorMessage()`, the same helper the create dialog and the list error state
use. `ui/p47-refusal.png`, from the same browser session as the HEAD pass:
`This profile still has 3 posts. Delete them before deleting the profile.`

`chrome-devtools-axi console --type error` after that click holds exactly one
entry, Chrome's own network log line for the 409 (`Failed to load resource: the
server responded with a status of 409 (Conflict)`). No application error.

`src/db/orphaned-posts.test.ts` builds a scratch database
(`content_pipeline_orphans_check`), migrates it with the real

names the orphan and not the attached control, writes nothing without
`--delete`, removes only the orphan with it, and says `no posts without a
profile` over a clean table. The scratch database is the point. The script
deletes every orphan in whatever database it is pointed at, by design, so a
test of it must not be pointed at one holding somebody's rows.

`posts.profile_id` stays nullable. Making it `NOT NULL` would mean a migration
that first deletes rows whose owner cannot be determined, on every database
that has any, and a schema constraint is not worth that. The reasoning is in
`web/drizzle/README.md` beside the command, which is where an operator looking
at a strange row will be.
